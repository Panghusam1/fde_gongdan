# 项目演示：正常闭环与来源不匹配转人工

## 一条命令运行

```powershell
npm run demo
```

命令不需要外部模型密钥，通常约三秒完成。它会为两条路径分别创建全新的内存 PGlite 数据库，依次执行真实数据库迁移、官方资料种子、页面原文入库、知识审核与索引、工单检索、证据判断、风险判断和终态写入。

## 五分钟讲解顺序

### 第一分钟：业务问题

目标用户是设备生产、组装和维修厂商。现场人员确认厂区和设备型号后，系统立即创建草稿工单，持续记录检索、证据、风险、方案和现场结果。系统最多提出两版完整方案；来源不匹配、高危动作、证据不足或两版失败时转人工。

### 第二分钟：正常闭环

演示确认来源为 `NVE41300/05/zh-CN`：

1. 工单检索当前有效官方资料；
2. 数据库确认候选的编号、版本和语言；
3. 内容判断器引用第395页原文，判定可以直接回答；
4. 固定风险规则允许生成外部观察方案；
5. 系统保存一版方案和现场反馈；
6. 现场确认恢复，工单进入 `resolved`。

预期数据库结果：一条检索、一条证据判断、一条风险判断、一版方案、一条现场反馈、零人工接管。

### 第三分钟：来源不匹配

演示人工确认来源为 `NVE41300/04/zh-CN`，但数据库候选属于第05版：

1. 检索仍能召回正文相似的第05版片段；
2. 程序按编号、版本、语言精确过滤后得到零条候选；
3. 内容模型调用数为0；
4. 系统保存“不能回答”的证据判断；
5. 风险门按证据不足创建人工接管；
6. 工单进入 `awaiting_human`，方案数保持0。

这条路径说明“文本相似”不能覆盖“来源身份不一致”。

### 第四分钟：为什么这样设计

- 资料身份、厂区、设备、工单状态和风险上限是确定性业务边界，由数据库与程序负责；
- 正文是否支持问题需要语义理解，由模型负责；
- 协调助手只有一个，负责在许可表内选择窄工具；工具和数据库决定能不能执行；
- 原始自由文本不进入来源确认后的内容判断模型，防止用户文字改写版本身份。

### 第五分钟：怎样证明不是“能跑一次”

- 真实 `qwen3.7-plus` 完成20案例40轮协调决策评测；
- 40题检索复测中 E5 前三命中100%，同时保留首位不足问题；
- 第四批结构化来源首次真实未见11/12，五条无匹配来源程序拒绝5/5，错误来源接收0；
- 全量自动化测试覆盖数据库约束、权限、检索、证据、风险、两版方案、工单终态和历史散列封存。

## 演示中哪些是真实的

- 24份数据库迁移和约束；
- 施耐德 NVE41300 中文05版的文件身份、页面原文和知识来源链；
- 工单、检索、证据、风险、方案、反馈和接管的事务写入；
- 第四版结构化来源过滤；
- 两条路径的数据库终态。

## 演示中哪些是可控的

- 为了离线、快速和可重复，演示的向量与模型决策使用确定性可控实现；
- 演示不是新的模型准确率测试，真实模型成绩以冻结首跑报告为准；
- 低风险用途尚未经过 ATV320 领域工程师批准，不能把演示方案当作维修指导。

## 自动验收

`tests/project-demo.test.ts` 固定验证：

- 正常路径最终 `resolved`，一版方案、零接管；
- 来源不匹配路径最终 `awaiting_human`，零方案、一条接管；
- 来源不匹配时内容模型调用数必须为0。

## 常见演示追问

### 为什么不用真实模型做现场演示？

现场演示的目标是稳定展示业务流程和数据库终态。外部网络、费用和模型波动会污染流程演示；真实模型能力已经用独立的首跑前封存测试验证，两类证据不能混在一起。

### 为什么来源不匹配不是直接报系统错误？

检索本身成功，只是没有符合人工确认身份的证据。这是可审计的“证据不足”业务结果，应保存判断并转人工，而不是伪装成技术故障。

### 这是不是多个智能体？

不是。项目使用一个协调助手加多个窄工具。证据判断模型和向量模型是受控能力组件，不拥有独立业务目标，也不能自行修改工单状态。
