# 资料检索与智能工单架构 v1

状态：v1主链路、40题开发评测与24题无答案留出测试已实现，等待答案存在性和生产条件验证
适用范围：第一周独立项目——工业设备故障资料检索与智能工单助手
示例设备：施耐德 ATV320 变频器
当前业务边界：厂区与设备确认后创建草稿工单；AI 最多给出两版有证据的低风险处置方案；现场人员确认实际结果；高风险必须转人工。

## 1. 这套系统最终要做出什么

用户不是来和一个“会聊天的机器人”闲聊，而是要完成一张可追溯的维修工单。

完整过程如下：

1. 确认用户有权访问的厂区。
2. 确认设备实例和标准型号。
3. 立即创建草稿工单。
4. 持续记录报警、现象、已执行动作和现场结果。
5. 从正确型号、正确版本的官方资料中找证据。
6. 先执行不可绕过的危险检查。
7. 高风险直接阻断 AI 处置并转人工工程师。
8. 低风险时，AI 根据证据生成完整处置方案，等待现场人员确认。
9. 第一版失败后，只有出现新证据时才能生成第二版；仍失败则转人工。
10. 只有现场人员确认恢复后，工单才能进入已解决状态。

因此，系统的核心产物不是一段回答，而是：

- 一张状态完整的工单；
- 一组不可删改的过程事件；
- 一次可复现的资料检索；
- 一次风险判断；
- 最多两版带出处的处置方案；
- 一份现场确认或人工接管记录。

## 2. 哪些部分由程序决定，哪些部分交给 AI

### 2.1 程序负责不可违反的规则

- 用户是否属于该厂区；
- 设备是否属于该厂区；
- 型号与资料是否匹配；
- 工单状态能否转换；
- 是否已经生成两版方案；
- 是否命中明确的高危规则；
- 是否允许关闭工单；
- 所有写操作是否留下审计记录。

这些规则不能只写在提示词里，也不能让 AI 自己判断是否遵守。它们必须由数据库约束和 TypeScript 业务代码共同执行。

### 2.2 AI 负责需要理解语言的工作

- 把现场人员的自然语言整理成结构化现象；
- 从检索结果中提取与当前故障有关的证据；
- 发现缺失但值得补充的信息；
- 根据证据草拟一套完整、易执行的低风险方案；
- 对不能确定的内容明确表示证据不足。

AI 可以建议调用哪个工具，但不能直接执行任意数据库语句，不能自行更改工单状态，也不能把工单标记为已解决。

## 3. 官方资料如何进入系统

### 3.1 原始资料层

每一份下载的官方手册先作为原始文件保存，至少登记：

- 来源网址；
- 发布者；
- 文件名；
- 文档编号；
- 适用设备系列与型号；
- 语言；
- 版本或发布日期；
- 下载时间；
- 文件的 SHA-256 摘要；
- 当前是否为有效版本。

原文件不覆盖。资料更新时新增版本，并让旧版本失效。这样才能回答“当时系统依据的是哪一版手册”。

### 3.2 第一解析器：PDF.js

第一周主路径采用 PDF.js：

- 它可在 TypeScript / Node.js 环境中直接读取 PDF；
- 能保留页码，方便生成可核验的引用；
- 不需要额外维护 Python 解析服务；
- 适合带正常文字层的设备手册。

它不是因为“最先进”而被选中，而是因为它与本项目的 TypeScript 技术栈、三天全量交付周期和页码追溯要求最匹配。

### 3.3 备用解析器：Docling

以下情况触发备用处理：

- 扫描版 PDF 没有文字层；
- 表格被严重打散；
- 阅读顺序错误；
- 警告框、标题和正文无法正确关联。

此时使用 Docling 做离线转换和文字识别。它支持版面分析、表格结构和文字识别，但处理更重，也会增加依赖，因此第一周不把它做成常驻在线服务。

### 3.4 解析质量关卡

资料不能“解析成功就算完”。每个版本都要过以下检查：

1. PDF 页数与解析页数一致；
2. 关键型号可以搜到；
3. 已知故障码可以搜到；
4. 引用能返回原始页码；
5. 随机抽查的警告、表格和步骤顺序正确；
6. 空白页和乱码比例在可接受范围内；
7. 解析失败时进入人工复核队列，不进入正式检索库。

AI 生成的摘要、关键词和标签只能作为辅助字段，不能覆盖原文。

## 4. 手册如何切成可检索的小段

### 4.1 不采用机械等长切分

设备手册中，一个警告、故障码解释和对应操作不能被随意拆开。因此采用“按结构切分”：

- 标题与其正文放在一起；
- 一个故障码及其含义、原因、检查步骤尽量保持完整；
- 一个安全警告与它约束的操作保持完整；
- 表头与相关数据行保持完整；
- 跨页但语义连续的段落可以合并；
- 同一页两段不相邻但共同证明一个条件时，保存两组精确范围，不把中间噪声强行带入。

### 4.2 第一轮不先冻结统一字数

项目先用OHF真实页面验证故障条目、阈值、复位条件、警告块和步骤块的边界，没有把“400—800字”写成正式规则。后来接入固定版本E5并完成10题基线，结果仍不足以证明统一字数优于结构边界，因此继续保持结构优先。第三天40题复测中，E5的正确片段30/30进入前三，也没有出现支持改为统一字数切片的新证据，所以结构优先继续保留。

接入嵌入模型后，长度只作为兜底：结构块超过模型实际输入上限时才继续拆分；是否合并小片段由标题、内容种类和安全边界共同决定。最终参数由同一批OHF问题的检索结果决定。

### 4.3 每个资料段必须携带的信息

- 来源版本编号；
- 具体页面提取结果、页内起止字符和逐字摘录；
- 章节路径；
- 设备系列和标准型号；
- 故障码、参数号等精确标识；
- 内容类型：警告、原因、检查步骤、参数表等；
- 是否包含安全信息；
- 原文；
- 内容摘要值，用于发现重复或变更。

切分程序和参数也必须有版本号。同一份手册换了切分方法，不能悄悄覆盖旧结果。候选创建服务不接受自由填写的机器原文，只接受页面提取编号和逐字摘录；程序定位唯一位置并从来源拼出机器原文。

## 5. 什么进入关系数据，什么进入向量

PostgreSQL 是关系数据库。工厂、设备、用户权限、工单、工单事件、风险判断、处置方案、资料版本等有明确字段和关系的数据，都以普通关系表存储。

向量不是另一个业务真相库。它只是某个资料段经过某个嵌入模型计算后得到的一串数字，用来寻找“意思接近”的段落。

本项目把向量放在独立记录中，并关联到资料段：

```text
资料段原文 ── 资料段编号 ── 向量记录
                           ├─ 模型名称
                           ├─ 模型版本
                           ├─ 向量维度
                           └─ 向量数值
```

这样做可以：

- 原文仍是唯一可引用证据；
- 同一资料段可以比较多个嵌入模型；
- 换模型时不覆盖旧结果；
- 可以重放一次历史检索；
- 可以删除无效向量而不损伤原始资料。

## 6. 第一版嵌入模型怎么选

### 6.1 基线：multilingual-e5-small 的 TypeScript 版本

第一版选择 `Xenova/multilingual-e5-small`，通过 `@huggingface/transformers` 在本地生成向量：

- 可直接进入现有 TypeScript 工程；
- 支持中英文资料与中文现场描述；
- 输出 384 维向量，适合目前的小型资料库；
- 不需要把手册内容发送给第三方接口；
- 没有模型调用费用，测试可重复。

数据库必须记录精确模型标识、提交版本、输入前缀、维度、池化方式、是否归一化和输入正文摘要。模型文件本身还要核对SHA-256。只写“用了E5”不够复现。

模型首次下载需要联网；下载后可以本地运行。

### 6.2 对照候选：BGE-M3

BGE-M3 支持多语言，并把稠密检索、稀疏检索和多向量检索放在一个模型体系中，也支持更长文本。它值得作为后续对照模型，但第一周不直接作为主路径，原因是：

- 模型和运行成本更重；
- 完整能力通常需要更复杂的推理与检索服务；
- 三天项目首先需要建立可验证的基线，而不是一次引入所有能力。

这不是预先判定 E5 一定更准。第二天要用同一批工业故障问题比较模型，数据结果才有决定权。

### 6.3 生成模型与嵌入模型分开

嵌入模型负责“找意思相近的资料”，生成模型负责“读证据并草拟方案”，二者不是同一个职责。

当前开发环境没有检测到已配置的生成模型接口密钥。因此代码先定义统一的 `LanguageModel` 接口，不把业务逻辑绑定到某一家模型。资料解析、嵌入、检索、风险规则和状态机仍可先完成；进入真实方案生成前，必须配置一种真实生成模型，不能用假结果冒充完成。

## 7. 检索不是只查向量

工业手册里有大量 `OHF`、型号、参数号等精确标识。纯向量检索可能把相似但错误的型号或故障码排在前面。因此采用混合检索。

### 7.1 完整检索顺序

1. 检查用户、厂区和设备权限。
2. 根据标准型号过滤资料范围，只保留有效的官方版本。
3. 提取并精确匹配型号、故障码、参数号。
4. 执行中文关键词检索。
5. 执行向量相似度检索。
6. 判断关键词第一名是否达到最低分且明显领先；有把握才使用倒数排名融合，否则以向量榜单为主。
7. 检查是否缺失正确型号、页码、版本或必要的安全信息。
8. 返回有出处的证据；证据不足则拒绝生成确定性方案。

### 7.2 为什么使用倒数排名融合

关键词检索分数与向量相似度分数含义不同，直接相加没有可靠依据。倒数排名融合只根据各自榜单中的名次进行合并，更容易解释和复现。

第一版让关键词检索和向量检索分别形成候选榜单，但关键词第一名至少3分且领先第二名至少2分时才参与融合。两个门槛属于当前分析器的实验参数，需要随题库扩大重新验证。

第一次10题实测中，无条件融合的第一名命中率只有60%，低于向量的90%。原因是OHF同时出现在定义、复位、阈值和禁用警告中，关键词榜单经常并列却仍污染排序。加入门控后，混合检索恢复到第一名90%、前三100%，与向量持平但没有超过向量。因此当前选择是“有门控的混合基线”，不是预设混合一定最好。

### 7.3 为什么第一周不用近似向量索引

本周只有少量官方资料，精确计算向量距离即可，结果稳定且容易检查。只有数据增长后，测得查询确实变慢，才考虑 HNSW 等近似索引。

索引不是“用了向量数据库就必须建”的装饰。

### 7.4 为什么先不加 AI 重排，后来又做受控试验

已经比较以下三条基线：

- 只用关键词；
- 只用向量；
- 关键词与向量融合。

10题初测表明主要问题是弱关键词污染，因此当时先增加可解释的信心门控。40题复测后，E5正确片段30/30进入前三、却只有23/30排第一，问题已经明确集中在细排，所以满足了试验二次排序的前提。项目随后实现`qwen3-rerank`适配器、返回结构校验和90%首位门槛；真实调用因现有Token Plan密钥不具备业务空间后端权限而在模型计算前返回401。它目前只是可测试的候选方案，没有接入主链路。

## 8. Agent 采用什么排布

### 8.1 选择：确定性状态机 + 一个协调 AI + 窄权限工具

系统只有一个面对用户的协调 AI。它理解描述、选择只读或受限工具、整理证据并草拟方案；工单状态和安全规则由确定性状态机控制。

```text
现场用户
   │
   ▼
协调 AI ──提出工具请求──► 工具权限层
   ▲                         │
   │                         ├─读取工单上下文
   │                         ├─检索官方资料
   │                         ├─追加现场观察
   │                         ├─执行风险判断
   │                         ├─保存方案草稿
   │                         └─请求人工接管/用户确认
   │                         │
   └────结构化结果──────────┘
                             │
                             ▼
                     状态机与数据库约束
```

### 8.2 工具清单

协调 AI 只能使用以下窄工具：

- `get_work_order_context`：已实现；读取当前工单、设备、最近证据和当前允许动作；
- `search_official_knowledge`：已实现；从工单推导设备和产品族，执行可记录的混合检索，返回官方版本、页码和逐字引用；
- `append_observation`：已实现；追加一条现场现象或已做动作，不改写历史；
- `run_risk_assessment`：已实现；执行固定规则，模型只能提高风险，高危或证据不足时原子创建人工接管；
- `draft_resolution_proposal`：已实现；保存完整的带证据方案，检查新证据和方案动作风险；
- `request_user_confirmation`：已实现；二次验证方案后进入等待现场确认；
- `record_user_confirmation`：已实现；保存现场实际结果，确认恢复、返回排查或在第二版失败后转人工。

人工接管不是协调模型可以自由选择的通用工具，而是风险判断、无新增证据或两版失败后的确定性结果。

明确不提供：

- 通用 SQL 工具；
- 任意修改工单状态的工具；
- AI 直接标记“已解决”的工具；
- 删除或覆盖历史事件的工具。

资料建设阶段另外提供窄工具 `create_knowledge_chunk_candidate`：协调 AI 可以提出页面原文摘录和分类建议，服务负责逐字定位并固定创建待审核记录。资料批准属于人工审核权限，不向协调 AI 提供。

`search_official_knowledge`不接受厂区、设备、型号或产品族作为模型参数。这些范围由工单关系自动推导；模型计算结束后服务再次验证授权和设备范围，再把检索运行、命中排名和工单事件原子写入。没有成功留痕的结果不能进入后续方案生成。

### 8.3 风险判断的三层防线

1. **明确规则层**：命中触电、拆机、带电测量、制动异常等预设规则时直接阻断。
2. **语义识别层**：AI 可以发现规则未覆盖的可疑风险并提高风险等级。
3. **流程控制层**：状态机再次检查风险结果、证据和方案次数，决定是否允许进入等待现场确认。

AI 可以把风险提高，但不能把明确规则已经阻断的风险降下来。

### 8.4 两版方案如何落实

- 第一版方案必须引用检索证据；
- 现场反馈失败时，先记录新观察；
- 只有出现新的现场信息或新证据，才允许第二版；
- 第二版失败、仍无新证据或任何时候命中高危规则，转人工；
- 数据库和状态机共同禁止第三版。

## 9. 为什么现在不做多 Agent

### 9.1 纯固定流程不够

它安全、易测试，但不擅长理解不规范的现场描述，也不能根据多段资料组织出完整方案。

### 9.2 一个完全自主的 AI 不合适

它看似灵活，但如果同时拥有检索、写数据库、改状态和关闭工单的权限，错误会直接变成业务事实，难以审计。

### 9.3 多 Agent 暂不合适

多 Agent 适用于能够真正并行拆分的开放式研究，例如多个子任务同时搜索不同方向，再由协调者汇总。本项目却是一条共享同一工单状态的顺序流程：确认设备、找证据、过风险关、出方案、等反馈。

此时拆成多个运行时 Agent 会引入：

- 重复检索和重复模型费用；
- 多个 Agent 对同一工单状态的竞争；
- 更复杂的权限与审计；
- 更难复现的失败路径。

因此第一周选一个协调 AI。开发和验收阶段仍可设置“资料审核、检索评测、安全审查”三个审查角色，但它们是测试岗位，不是生产运行时的三个自治 Agent。

### 9.4 为什么不先引入重型 Agent 框架

当前只有一个协调 AI、七个窄工具和固定状态。使用 TypeScript 明确写出状态转换表、工具接口和模型适配器，更容易读懂、测试和审计。

未来只有在出现长时间等待、跨系统回调、大量失败重试和复杂并行分支时，才评估持久化工作流框架。第一周不为了“架构看起来高级”增加依赖。

### 9.5 证据判断为什么改成两阶段固定流程

18道新三分类题证明“单次模型直接给最终类别和证据”不够稳定。当前候选策略改为：第一次模型只核对是否同一业务对象、问题前提是否有依据、最终所求事实是否有依据；程序固定生成类别；只有直接回答或部分相关时，第二次模型才选择候选、页码和连续原文，随后由程序验证。

这不是新增多个智能体。所有顺序、分支和停止条件都由协调代码固定，同一个千问模型只完成两个窄任务。选择它的原因是本业务规则清楚、风险边界固定，需要可预测和可审计；代价是相关题模型调用从一次变为两次。R255在已暴露题上的原联合门槛16/18仍记失败；保持策略不变后，R262在第三批18道项目内未见问题上类别与多证据联合均17/18并通过冻结门槛。由于问题和标签尚未获得领域工程师审核，该架构仍未获得生产批准。

“页面位置不能决定知识边界，业务目的和风险边界才能决定知识边界。”同一表面词只有在产品、对象和业务目的相同时才可作为相关证据；财务OHF、网站错误检测和办公服务器重启不能因为词语相同进入变频器维修答案。

## 11. 如何用测试决定架构对不对

### 11.1 已建立40条问题的固定开发测试集

题库现为30道可回答、5道错ATV产品族、5道当前六片语料无答案。30道正向题按六个候选各5题，并覆盖手册原词、现场口语和语义改写；每题绑定真实候选和PDF页，拒答题绑定原因。它是项目开发集，不等于真实工厂查询分布。

复测结果：E5首位76.7%、前三100%；门控混合首位73.3%、前三100%；错型号经过产品族前置门后5/5拒答且不调用向量模型；当前语料无答案题仍是0/5拒答。随后0.86候选阈值在独立24题留出集上仅正确拒答10/12、接收准确率11/13，未达到冻结门槛，因而没有接入主链路。

### 11.2 第一周验收目标

- 跨型号资料泄漏：0；
- 返回结论的引用完整率：100%；
- 预设高风险测试的阻断召回率：100%；
- 正确证据进入前 5 名：目标不低于 90%；
- AI 直接关闭工单：0；
- 允许生成第三版方案：0。

这些是本项目测试集的验收线，不宣传成真实工厂已经达到的生产指标。

### 11.3 必须做的对照实验

同一批问题分别运行：

1. 关键词检索；
2. 向量检索；
3. 混合检索；
4. 已实现但尚未取得合法后端密钥完成真实验收的二次排序。

记录每次命中、排名、耗时、错因和资料版本。以后更换模型或切分参数时重跑，AI 才能用测试数据审查自己，而不是对自己的设计做口头保证。

## 12. 三天内如何无删减落地

| 天数 | 要做出的东西 | 要学会的东西 |
|---|---|---|
| 第一天 | 业务流程、数据库、官方资料、来源审核、本地E5、三种检索基线和工单范围检索工具 | 把业务规则分成数据库约束、程序规则和AI判断；理解关系数据、向量、来源与评测的分工 |

任务总量与原五天计划相同，不把40题、完整主流程、重构、演示或面试材料降为可选项。

## 13. 本阶段建议整体验收的五项决定

1. PDF.js 为主解析器，Docling 只作为复杂文档备用处理器。
2. 采用按手册结构切分，长度只作为实验参数。
3. 本地 multilingual-e5-small 作为第一版嵌入基线，BGE-M3 作为后续对照候选。
4. 保留精确标识、中文关键词、向量和有信心门控的倒数排名融合作为对照；40题上混合没有超过纯E5，二次排序只作为尚未验收的候选，不接入主链路。
5. 采用确定性状态机 + 一个协调 AI + 窄权限工具，不采用运行时多 Agent，也不先引入重型 Agent 框架。

五项第一版均已落地。协调助手已经跑通普通恢复、第二版恢复、两版失败、高危和无证据五条确定性端到端路径；真实`qwen3.7-plus`也已完成基础调用和20案例40轮过程评测。40题检索复测已经完成，并据此增加错产品族硬拦截和与检索排名解耦的输入高危意图门，同时启动二次排序与无答案阈值试验。24题留出测试已经否决0.86阈值，下一步改为评估候选是否直接回答问题；另需取得合法后端排序密钥执行R196，并用真实模型驱动真实工具验证数据库终态。
