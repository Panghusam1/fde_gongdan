# 阶段五面试题：产品级知识审核与自动审计

- 项目：ATV320 变频器智能工单系统
- 阶段日期：2026-08-18
- 阶段范围：审核授权、一键确认、修正与驳回、自动前后快照、事务回滚
- 本阶段规则：R113—R123
- 当前验证：全项目116项自动化测试通过，0失败

## 30秒介绍

我为工业知识候选实现了按产品族授权的人工审核服务。模型可以把分类、用途和正文建议一次填完整，但只有被授权到ATV320产品族的活动用户才能确认、修改或驳回。知识状态变化时，PostgreSQL触发器自动保存修改前后快照、审核人、时间和理由，事件不可更新或删除。服务用行锁防止重复审核，数据库拒绝矛盾分类时，状态和审计事件在同一事务中整体回滚。

## 为什么这是FDE工作而不是变频器工程师工作

FDE不判断维修结论，而是设计谁有权判断、判断时看到什么证据、修改怎样留痕、AI为什么不能给自己放行。设备工程师负责专业正确性，FDE负责让这份专业判断在系统里可信、可追溯、不可越权。

## 架构

```text
AI待审核候选 + 官方精确来源
  → 审核服务锁定候选
  → 验证用户启用状态与ATV320产品审核资格
  → 一键确认 / 修改后确认 / 说明理由后驳回
  → PostgreSQL检查最终字段
  → 状态触发器自动写前后快照
  → 正式知识或永久驳回记录
```

## 高频问题

### 1. 为什么不直接用厂区工程师角色？

厂区角色限定工单业务范围，产品审核资格限定知识专业范围。一个人在苏州厂是工程师，不代表他能审核所有厂商和型号的知识，所以单独建产品族审核资格。

### 2. 为什么不只保存最终审核结果？

只保存最终值无法知道AI错在哪里，也不能形成后续评测数据。审核事件保存修改前后快照，可以统计哪些字段经常被改、复盘错误并改进候选生成策略。

### 3. 为什么事件由数据库触发器写，不由服务写？

未来可能有管理后台、脚本和批处理等多个写入口。触发器以状态变化为统一入口，只要候选进入终态就自动留痕，降低某条代码忘记写事件的风险。

### 4. 为什么快照用 `jsonb`，不是全部拆列？

当前正式值需要筛选和约束，所以保留关系字段；快照只保存“当时整组值”，使用 `jsonb` 更适合审计。它不是拿JSON替代全部关系设计。

### 5. 一键确认是不是走过场？

不是。模型已经准备完整候选和官方证据，专业人员点击确认表示对照后同意；系统自动填“无修改”说明。只要修改任何建议字段，就必须填写具体理由。

### 6. AI怎样被阻止自动批准？

审核服务要求来自可信登录会话的用户编号，并检查该用户是否具有对应产品族资格；协调助手不暴露审核工具。当前本地案例还没有接入真实身份提供方，因此不能夸大为已经完成生产级身份隔离。

### 7. 两个人同时审核怎么办？

服务读取候选时使用行锁。第一个事务完成后，第二个请求看到状态已不是待审核并失败。数据库还规定已审核记录不可修改，并限制一个候选只有一条终态审核事件。

### 8. 服务和数据库怎样分工？

服务理解“当前用户是否有这个产品族资格”和“一键确认是否需要自动说明”；数据库保证字段组合、外键、状态、快照和不可变性。服务负责业务语境，数据库负责所有写入口都必须服从的底线。

### 9. 真实产品依据是什么？

IBM watsonx Orchestrate官方文档展示了提取结果触发用户审核、人员对照文档修改并提交后继续流程；Microsoft Document Intelligence官方透明度说明建议高风险场景保留人工监督。它们证明工作模式真实存在，不证明本项目已经被这些公司采用。

## 测试证据

专项测试覆盖：产品族资格唯一、自动保存前后快照、审核事件不可改删、一键确认、修改必须留理由、驳回、无资格、跨产品越权、重复审核，以及矛盾分类导致状态与事件一起回滚。
