# 阶段三面试题：知识片段来源链

- 项目：ATV320 变频器智能工单系统
- 阶段日期：2026-08-18
- 阶段范围：片段到具体页面提取结果的来源关系、审核前来源门禁、审核后冻结、真实OHF验证
- 本阶段规则：R78—R91
- 阶段完成时验证：全项目84项自动化测试通过，0失败；项目当前为105项通过

## 一、30秒介绍

在知识片段分类和审核之后，我继续补全了来源链。旧结构只存页码，无法区分同一页的 pypdf、Docling、光学识别或人工结果。我新增独立来源关系表，让一个片段可以按顺序连接多份具体提取结果，并用三层组合外键阻止跨版本和错页面拼接。没有来源的片段不能审核通过；审核后片段、来源关系和页面提取结果都不可原地改写。最后导入真实440页手册，从第72页 `pypdf 6.10.0` 结果建立了第一条OHF故障定义来源链。

## 二、两分钟介绍

页码只是位置，不是完整证据。同一页可能同时有多种工具结果，因此我比较了三种方案：只存页码无法指明具体结果；片段直接连接一个提取结果不支持跨页；独立来源关系表虽然多一张表，但支持多来源、顺序和工具版本追踪，所以选择第三种。

关系表有意重复保存资料版本、页面和提取结果编号，再使用三层组合外键分别核对“片段—版本”“页面—版本”“提取结果—页面”。这样即使所有编号分别存在，05版片段连接04版页面或第72页连接第50页提取结果也会被数据库拒绝。

审核流程改成先创建待审核候选，再绑定来源，最后人工确认。普通检查约束不能跨表判断有没有来源，所以用触发器阻止无来源片段通过。为了避免审核后的证据被替换，页面提取结果只允许新增；片段通过或驳回后，片段和来源关系都被冻结。旧库如果已有无来源的已通过片段，迁移会明确阻断而不是自动猜页码。

真实验证导入NVE41300全部440页，定位第72页实际文字指纹和 `pypdf 6.10.0` 结果，建立并审核 `[设备过热] OHF: 设备过热` 片段。最终能从片段反查故障码、页码、工具、版本和审核状态。

## 三、架构怎样讲

```text
官方文件
  → 资料版本
  → PDF页面
  → 具体提取结果（工具、版本、配置、正文指纹）
  → 片段来源关系（来源顺序）
  → 知识片段（三维分类、核对正文、审核记录）
  → 后续检索
```

一句话：检索返回的不只是答案文字，还必须能沿数据库关系回到当时审核的具体证据。

## 四、高频面试问题

### 1. 为什么保存页码仍然不够？

同一页可以有pypdf、Docling、光学识别和人工录入等多份结果。只保存页码无法说明采用了哪份正文、哪个工具版本，也无法比较工具升级前后的差异。

### 2. 为什么不用一个 `page_extraction_id` 直接放在知识片段表？

直接外键适合强制一片段一来源，但段落可能跨页，一条知识也可能需要按顺序连接警示框和解释。独立关系表支持一对多来源，且每条来源有顺序。

### 3. 为什么不用数组保存多个来源编号？

数组很难让普通外键逐项验证，查询、排序和去重也更复杂。关系表让每个来源成为独立记录，可以使用外键、唯一约束和索引。

### 4. 为什么关系表重复保存资料版本和页面编号？

这是受约束的重复，用来建立组合外键。它让数据库直接核对片段与版本、页面与版本、提取结果与页面，避免只凭应用程序查询后拼接。

### 5. 组合外键解决了什么普通外键解决不了的问题？

普通外键只能证明“这个片段存在”“这个页面存在”。组合外键还能证明“这个片段和这个版本是同一条记录中的组合”，因此阻止两个真实编号被错误拼在一起。

### 6. 为什么“至少一条来源”使用触发器？

它需要查看另一张表中是否存在关系记录。PostgreSQL检查约束只适合当前行，不应读取其他表；外键又只能保证已有关系有效，不能保证父记录至少拥有一个子记录。因此在更新为已通过时用触发器检查。

### 7. 为什么不能直接插入已通过知识？

正确顺序是先创建候选，再获得片段编号，随后绑定来源，最后审核。尚不存在的片段无法提前拥有来源，所以直接插入已通过记录必然缺少来源链。

### 8. 为什么页面提取结果不能修改？

否则片段仍指向同一编号，但编号背后的正文已经变化，审核记录就失真。新工具或修正结果应该新增一条提取记录，旧记录用于还原历史。

### 9. 已通过片段发现错误怎么办？

当前第一版不原地修改，而是新建候选、绑定正确来源并重新审核。旧片段保留，保证旧工单可以还原。以后可增加显式修订关系和撤回状态。

### 10. 为什么迁移遇到旧的已通过片段要失败？

因为新来源表刚创建时无法可靠知道旧片段采用了哪一种提取结果。自动按页码猜测可能连错工具结果；悄悄降级会改写审核事实。阻断迁移让问题显式暴露。

### 11. 真实数据怎样验证这套设计？

测试导入真实440页提取文件，查到第72页文字指纹为 `e8e2fddc584251547b8364c8a25faeba2058a5ea6cc1b13fefb42a0e231d9056`，确认其中包含OHF定义，再建立来源关系和审核记录。不是只用手写假文本验证表结构。

### 12. 哪些实际产品有相似思想？

Microsoft Azure AI Search 的结构化切片给片段保存父级来源字段；Google Cloud Document AI 保存文档修订及修改来自人员还是处理器；IBM watsonx Orchestrate 让审核人把提取值和源文档并排比较。它们证明来源父级、处理版本和人工复核都有真实产品背景，但不代表使用了我们的三层组合外键。

### 13. 这个阶段结束时还有什么缺口？

这个阶段结束时，来源只精确到页面提取结果，还没有页内起止位置和正式候选创建服务。阶段四已经补上这两项；目前仍没有片段修订关系、E5向量和检索评测。
