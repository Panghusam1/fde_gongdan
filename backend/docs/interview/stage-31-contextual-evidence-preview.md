# 阶段三十一：工单级证据绑定与可读性修正

## 30秒介绍

在多工单页面验收时，我发现一个会破坏演示可信度的重大漏洞：切换 13 张工单后，中间证据区始终显示同一张 OHF 图片、同一页码和同一段摘录。排查确认后端已经返回每张工单自己的阶段、问题、分支和资料版本，错误发生在前端——证据模块完全写死。修复时没有虚构 13 份资料，而是让后端按业务状态返回工单级证据预览，前端只按状态渲染。最终形成已核验手册、高危阻断、证据不足、版本冲突、权限阻断和尚未检索六类界面；只有真正通过资料核验的工单可以显示手册图片和原文。

## 问题为什么严重

这不是普通的图片复用问题。同一份官方手册可以被多个工单合法引用，但必须满足三个条件：当前工单已经发生检索、问题属于这份资料的能力范围、请求的资料身份与库内资料一致。旧页面绕过了这些条件，导致尚未检索、高危阻断、越权访问、资料不匹配和证据不足的工单也显示“已核验手册摘录”。页面展示因此与系统真实决策链冲突。

## 根因追踪

```text
冻结评测集
  └─ 每条案例都有 observation / query / branch
       ↓
后端工单目录
  └─ 已返回 stage / branch / manualSource / query
       ↓
前端工单选择
  └─ selectedWorkOrder 正确变化
       ↓
旧证据组件
  └─ 图片、页码、摘录全部是 JSX 固定文本  ← 根因
```

浏览器切换工单时，标题、厂区和问题都正确变化，只有证据区不变；代码检查进一步发现证据组件没有读取 `selectedWorkOrder` 的证据字段。这证明问题不在数据库或接口缓存，而在前端把“演示素材”误当成“工单证据”。

## 方案比较

### 方案一：按工单号在前端换图片和文案

实现快，但业务判断散落在页面中，新增工单需要继续修改组件，而且容易再次把不存在的证据写进界面。否决。

### 方案二：给 13 张工单各造一张不同图片

视觉上不同，但会制造没有来源支持的伪证据，违反项目的数据边界。否决。

### 采用：后端返回结构化证据状态，前端按状态展示

后端利用冻结数据已有的 `stage`、`branch`、`query` 和 `manualSource` 生成 `evidencePreview`。前端不再判断业务真伪，只展示状态、来源、当前核验问题和解释。只有 `verified_manual` 能携带页码、原文和手册图片，其他状态必须把三项设为空。

## 六类证据状态

| 状态 | 触发条件 | 页面展示 | 是否显示手册图 |
|---|---|---|---|
| 尚未检索 | 工单仍在接入或资料限定阶段 | 待检索、当前问题、尚未产生检索记录 | 否 |
| 已核验手册 | 已完成检索且官方原文可以回答 | 资料身份、第395页、原文、本工单核验问题 | 是 |
| 高危阻断 | 输入命中确定性高危规则 | 命中请求、停止自动处理、转人工 | 否 |
| 证据不足 | 问题属于维修历史或库存等现场数据 | 说明官方手册的能力边界 | 否 |
| 版本冲突 | 用户确认04版，知识库只有05版 | 请求版本与可用版本冲突 | 否 |
| 权限阻断 | 请求方没有当前厂区访问权 | 权限校验失败、检索未发生 | 否 |

## 自动化验证

- R329：抽查 U301、U303、U308、U310、U312 和资料版本不匹配案例，证据状态必须与阶段和分支一致；
- R330：遍历全部 13 张工单，只有 `verified_manual` 可以携带图片、页码和摘录；其他状态必须是状态卡，页码和摘录为空；
- 前端回归：组件必须读取 `selectedWorkOrder.evidencePreview`，不得保留固定 blockquote；
- 浏览器验证：依次切换六类代表工单，确认状态、图片有无和核验问题同步变化。

本阶段最终完整回归：后端共 323 项，296 项通过、0 失败、27 项按登记跳过，耗时约 127.1 秒；前端 77 项全部通过，代码规范、类型检查和生产构建均通过。

## 可读性调整

第一次从 7—10px 提高到 10—13px 后，真实 1280×720 窗口仍偏小。本阶段再次提高为：基础字号 15px、工单标题 15px、面板标题 14px、事实字段 12px、证据正文 15px、当前工单标题 21—26px。代价是小窗口需要纵向滚动，但现场演示的可读性优先于把全部信息强塞进一屏。

## 高频面试问题

### 1. 同一张手册页为什么还能在多张工单中出现？

因为 U303—U307 的问题确实都落在同一个 OHF 官方条目上。正确做法不是为了视觉不同而伪造来源，而是展示相同来源、不同的本工单核验问题。尚未检索、高危、越权、证据不足或版本不匹配的工单则不能显示这张手册页。

### 2. 为什么证据状态由后端决定？

证据是否存在属于业务事实，不是界面装饰。若前端按工单号自行判断，网页与正式主链路容易产生两套规则。后端返回结构化状态，前端只负责展示，可以让接口测试和界面测试共同约束同一个事实。

### 3. 自动化测试为什么之前没发现？

原测试只检查“页面里有证据图片和关键栏目”，没有检查切换工单后证据是否变化，也没有建立“非已核验工单不得显示摘录”的反向约束。新测试增加了跨工单状态抽查和全量不变量，覆盖的是业务一致性而不是单个元素是否存在。

## 问题与调整台账

| 异常现象 | 定位证据 | 根因 | 调整 | 复测 |
|---|---|---|---|---|
| 13张工单证据区完全相同 | 切换后标题变化，图片/页码/摘录不变 | 前端证据 JSX 全部写死 | 后端增加结构化 `evidencePreview`，前端按状态渲染 | 六类代表工单浏览器切换通过 |
| 高危、越权案例仍显示“已核验摘录” | 页面内容与数据库流转计数冲突 | 展示层绕过证据门 | 非已核验状态禁止返回摘录、页码和手册图 | R330 遍历全部工单 |
| 第一次放大后仍难读 | 1280×720 实图检查 | 仍以高密度一屏容纳为目标 | 再提高至 12—15px 正文和 21px 以上主标题 | 浏览器计算字号复测 |

## 不能夸大的范围

- 工单证据状态来自冻结评测数据，不是客户生产现场实时回放；
- 同一 OHF 条目的多工单复用是事实，不代表系统拥有 13 份不同官方资料；
- 状态卡证明页面与当前项目规则一致，不等于已经接入企业库存或维修历史系统；
- 当前修复保证目录展示一致性，正式运行结果仍由独立演示接口和真实数据库链路产生。
