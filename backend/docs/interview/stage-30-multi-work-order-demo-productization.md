# 阶段三十：多工单现场演示与页面产品化

## 30秒介绍

我没有把参考截图当成模板复刻，而是从真实操作任务反推页面：左侧跨工单队列负责筛选和选择，右侧单工单工作区负责证据、风险、处置和审计。后端把 12 条冻结端到端评测工单和 1 条版本不匹配演示记录作为目录返回，覆盖六个阶段；其中五条可以从网页真实运行。为了让现场讲解有清晰主线，队列最上方固定正常闭环、高危转人工、来源不匹配三条主演示，其余证据不足和未授权厂区保留为扩展验证。页面明确区分项目评测数据与客户生产记录。

## 2分钟介绍

上一版页面虽然像工业控制台，但它把用户给的参考图栏目和比例搬了过来，导致产品含义错误，也在宽屏产生大面积空白。我先重新梳理操作对象：队列是跨工单对象，证据、风险、安全和时间线都是单工单对象，所以页面不能是“左队列、中详情、右全局审批、底部全局时间线”的照抄三栏，而应是“左队列 + 右完整工作区”。

数据上没有为填满队列编造客户记录。我复用首次运行前已经冻结的 `work-order-end-to-end-holdout-v3` 12 条案例，再增加项目原有的来源不匹配演示分支。后端目录显式返回来源案例号、阶段、状态、预期数据库计数和 `productionRecord: false`。前端未运行时只显示冻结预期，运行后才显示本次实际。

工程上先补失败测试，再扩展场景运行器和目录接口。五条演示都重新创建 PGlite、执行迁移、导入正式知识数据并走真实工具和状态逻辑。浏览器验证不仅看按钮文字，还检查 1280/1920 实际边界框、页面滚动宽度和五分支数据库计数。测试曾全部通过但浏览器仍出现横向隐式列，这说明静态断言不能代替视觉和交互验收。

## 架构与数据流

```text
冻结评测集12条 ─┐
                 ├─ 工单目录构造器 ─ GET /api/work-orders ─ 左侧队列/筛选
来源不匹配1条 ──┘

选中可演示工单
  → POST /api/demo { scenario }
  → 全新 PGlite + 真实迁移 + 正式知识种子
  → 厂区权限 / 来源过滤 / 检索 / 证据判断 / 风险规则 / 状态流转
  → 工单终态 + 模型调用次数 + 七类数据库计数
  → 右侧工作区同步刷新
```

## 决策：为什么是两栏而不是参考图三栏

### 备选一：完整照抄参考图

优点是短时间内视觉相似。缺点是参考图里的审批栏和全局时间线不一定符合我们的对象关系，而且会制造不存在的业务字段。否决。

### 备选二：只做一条工单详情

实现简单，但不能体现工单运营、阶段分布和多分支演示，也不能回答“系统如何处理不同状态的工单”。否决。

### 采用：跨工单队列 + 单工单工作区

队列和筛选解决跨记录管理；事实、证据、安全和时间线归属当前记录。该结构与微软 Field Service、IBM Maximo 的“工单列表/视图 + 状态生命周期 + 工单详情/历史”原则一致，但页面布局和字段从本项目业务独立设计。

## 高频问题

### 1. 队列数据是真实的吗？

是真实用于本项目评测和回归的数据，不是虚构的界面占位符；但它们不是客户生产工单。页面和接口都明确标出这个边界。

### 2. 为什么阶段展示记录不能全部点击运行？

队列的首要作用是展示完整阶段分布。只有已经进入受控演示白名单的五条场景允许运行，以保证输入、时长、安全边界和结果可复现。不能为了“每条都能点”在前端模拟结果。

### 3. 为什么未授权厂区最终仍是“处理中”？

它在权限校验前停止，没有检索、判断、方案或人工接管记录，因此不能伪造已解决或等待人工。当前状态反映数据库真实结果，也暴露后续可以增加专用拒绝终态的产品改进点。

### 4. 参考成熟企业产品，为什么不直接复制它们的界面？

企业案例用于验证业务模式是否成熟，不用于替代本项目设计。我们借鉴“状态生命周期、队列、详情、历史”的原则，字段、分区和交互仍由当前业务对象与风险边界决定。

### 5. 自动化测试通过为什么还要看浏览器？

测试验证了接口、文案、选择清理和关键样式声明，但浏览器最终计算布局时，旧命名网格区域让新工作区生成了隐式横向列。只有实图和边界框测量暴露了问题。因此页面验收必须包含代码测试、真实浏览器布局和真实后端分支三层。

## 问题与调整台账

| 原方案/现象 | 定位证据 | 根因 | 调整 | 复测 |
|---|---|---|---|---|
| 参考图上的“界面设计概念”被搬到成品 | 用户指出并非要求照抄 | 把参考图当模板而不是质量样例 | 删除该文案，重建两栏业务结构 | 组件测试禁止该文案 |
| 队列只有两条 | 后端仅接受 `normal/source_mismatch` | 演示运行器和接口白名单过窄 | 从冻结评测集构建 13 条目录，扩展五个场景 | 目录接口和场景接口测试通过 |
| 页面宽屏空白严重 | 旧样式 `width:min(100%,1540px)` | 作品集居中容器思路不适合操作台 | 全视口宽高、队列和正文内部滚动 | 1920 宽文档无横向溢出 |
| 测试绿但模块横向溢出 | 浏览器计算出右侧两列隐式网格 | 旧 `grid-area: timeline/safety` 污染新父网格 | 父工作区明确单列，子项清除旧区域名 | 浏览器边界框复测通过 |
| 高屏下方仍有空区 | 内容列按自然高度结束 | 剩余高度没有分配给证据和留痕 | 证据、数据库区使用剩余高度 | 1920×1080 复查通过 |
| 字号过小，五条可运行案例没有演示主次 | 1280×720 实图中信息可读性弱，讲解入口分散 | 沿用了高密度监控台的小字号，并按数据原顺序展示 | 建立 10—18px 的分级字号；固定三条主演示在队列顶部，另两条标为扩展验证 | 浏览器确认前三条顺序和 13/13px 主体字号 |
| 放大字号后筛选栏出现横向滚动条 | 筛选容器 `scrollWidth` 超过 299px 可视宽度 | 容器仍使用单行 `overflow-x:auto` | 改为按钮自动换行并取消局部横向滚动 | 1280 宽下 `scrollWidth = clientWidth = 299px`，整页也无横向溢出 |

## 不能夸大的范围

- 13 条是项目评测/演示记录，不是企业生产数据规模；
- 五条受控场景证明项目逻辑可运行，不证明开放输入下的全部维修能力；
- PGlite 每次从零创建适合可重复演示，不代表正式 PostgreSQL 的并发和持久化方案；
- 页面本地联调通过，不代表公网生产部署；
- 官方手册证明资料内容，不证明方案经过现场工程师认证。
