# 阶段七面试题：工单范围检索工具与全过程留痕

- 项目：ATV320变频器智能工单系统
- 阶段日期：2026-08-18
- 阶段范围：Agent窄工具、工单范围推导、二次验权、检索审计、完整引用和幂等重放
- 本阶段规则：R136—R143

## 30秒介绍

我把底层混合检索封装成工单范围内的`search_official_knowledge`窄工具。AI不能传厂区、设备或产品族，而是由服务从工单自动推导，并检查当前登录成员属于工单厂区。模型推理在事务外执行，写入前重新验权；检索运行、原始关键词/向量排名、最终结果和工单事件在同一短事务中保存并禁止篡改。每条结果带官方资料编号、版本、文件摘要、PDF页码和逐字摘录，撤回版本返回0条但检索过程仍留痕。

## 2分钟介绍

底层检索函数需要产品族编号，但这个参数不能直接交给AI，否则它可能传错型号或被提示注入诱导查询其他产品资料。我设计的工具只接受工单、会话注入的厂区成员、问题、返回数量和幂等键。

服务先从工单连接现场设备、规范型号和产品族，再验证成员与用户账号均启用且属于同一厂区。通过后在事务外计算查询向量。因为模型调用期间权限或设备关联可能改变，所以保存前在短事务中重新检查同一组范围。

数据库使用复合外键保证工单—厂区—设备、设备—型号、型号—产品族和成员—厂区不能拼错。一次检索写入运行表，多条结果批量写入命中表，并向工单时间线追加`knowledge_searched`事件；三者任一步失败都会回滚。运行和命中记录只能追加，不能事后改问题或名次。

工具不仅返回正文，还批量回查发布方、资料编号、官方网址、版本、SHA-256、页码、字符范围和逐字摘录。检索还要求手册版本为当前有效，撤回后即使知识片段曾经通过审核也不再返回。零命中仍保存，供后续流程转为补充信息或人工接管。

## 架构

```text
协调助手
  │ 工单 + 问题 + 幂等键
  ▼
search_official_knowledge
  ├─会话成员/用户验权
  ├─工单→设备→规范型号→产品族
  ├─当前资料版本 + 已审核知识
  ├─事务外关键词/向量检索
  ├─事务内重新验权
  └─检索运行 + 命中 + 工单事件
                     │
                     ▼
          官方编号/版本/页码/逐字摘录
```

## 重点：问题与调整台账

### 问题一：第一版工具返回“结果”，却没有返回“引用”

- 现象：能看到知识正文和排名，但无法向用户展示来自哪份手册、哪一版和哪一页。
- 根因：底层检索只关注排序字段，工具层没有补齐来源链。
- 调整：新增R141，并按所有命中片段一次批量查询来源，避免逐条查询。
- 结果：返回发布方、标题、编号、官方网址、版本、文件摘要、页码、字符范围和逐字摘录。
- 面试价值：说明搜索结果与可审计证据不是同一件事。

### 问题二：知识已审核，但手册可能已经撤回

- 现象：最初SQL只检查`knowledge_chunk.review_status = approved`。
- 风险：旧版或撤回手册的片段仍可能进入AI上下文。
- 调整：新增R142，两条检索路线都要求`source_version.version_status = current`。
- 回归：R129—R131随即失败。
- 定位：旧测试夹具没有把手册版本设为当前有效，并不是新SQL错误。
- 修复：只修正测试前提，保留生产门禁。
- 面试价值：展示如何区分“新规则导致合理回归”与“生产代码缺陷”。

### 问题三：停用账号被误报成工单不存在

- 现象：安全上成功阻断，但错误类型不准确。
- 根因：用户启用条件写在连接过滤中，停用用户把整行过滤掉了。
- 调整：新增R143，将授权结果作为明确布尔值返回，再统一判断。
- 结果：停用成员、停用用户和跨厂区成员都在模型调用前以授权错误拒绝。
- 面试价值：安全不仅要“拒绝”，还要保证错误可诊断、行为可测试。

### 问题四：模型计算期间权限可能变化

- 风险：第一次验权后到保存前存在时间窗口。
- 调整：模型计算放事务外，写入短事务时重新查询并比较厂区、设备、型号、产品族和授权状态。
- 验证：测试嵌入器在查询期间停用成员，服务最终拒绝且检索表、命中表和工单事件均为0。

### 问题五：Agent重试会重复花模型费用并污染工单时间线

- 调整：同一工单和幂等键形成唯一请求；完全相同则直接重放保存结果，不调用模型；内容冲突则拒绝。
- 验证：相同请求执行两次，查询向量只计算一次，检索运行编号相同。

## 高频问题

### 1. 为什么不让AI直接调用`searchApprovedKnowledge(productFamilyId)`？

产品族是由设备关系确定的业务范围，不是语言模型应该猜的参数。窄工具从工单推导范围，避免模型传错或越权。

### 2. 为什么不提供只读SQL？

只读仍可能读取其他厂区、用户或未审核资料，也容易被提示注入改变查询。工具应该只暴露完成当前业务所需的最小读取能力。

### 3. 为什么同时保存检索表和工单事件？

检索表保存算法细节，工单事件形成统一业务时间线。两者面向不同查询，但在同一事务中产生。

### 4. 为什么结果写入前要再次验权？

模型计算不在数据库事务里，期间用户可能停用或设备范围发生变化。二次验权保证使用结果时前提仍成立。

### 5. 为什么不把模型调用放事务里彻底避免变化？

长时间模型调用会占用连接和锁，降低并发并增加死锁风险。先计算、后短事务复核更合理。

### 6. 零结果为什么不抛异常？

没有当前有效证据是正常业务结果，后续应补信息或转人工。把它保存下来还能证明AI不是没有检索就自行回答。

### 7. 幂等键为什么还要核对问题和模型？

相同键不一定代表相同业务请求。只有问题、范围、模型和参数都一致才能重放，否则必须拒绝冲突。

### 8. 复合外键解决什么问题？

它不只检查编号各自存在，还检查多个编号在父表中属于同一业务关系，防止把真实工单、真实设备和真实产品族拼成错误组合。

### 9. 真实产品依据是什么？

Amazon Bedrock AgentCore Gateway把API和Lambda转换为带认证和策略的Agent工具；OWASP建议最小化Agent工具和权限，并由下游系统完成完整授权。它们支持窄工具和服务验权模式，不证明本项目使用AWS或照搬其内部实现。

### 10. 当前还缺什么？

真实身份中间件、生产数据库最小权限角色、资料版本发布审批服务、风险判断工具和方案生成都尚未完成。
