# 阶段二十三：来源感知证据与U301真实回归

## 30秒项目介绍

“新未见端到端测试唯一失败是用户点名 NVE41300 时，证据判断器拒答。我沿数据库来源链排查发现，资料编号、版本和语言在候选接口处被丢弃。我新增来源感知适配器，由程序根据检索命中反查数据库身份，再通过第六版两阶段判断器把来源字段结构化传给千问。真实 U301 回归从无答案变为直接回答并引用第 395 页，风险门允许生成方案；原 11/12 首跑仍保留。”

## 为什么资料编号不能只显示给用户？

因为问题可能要求判断“指定资料是否写了某件事”。这时资料编号参与事实成立条件，和正文同样属于证据。只在界面显示、不传给判断器，会造成信息不对称。

## 为什么不把编号拼进章节标题？

拼接虽然可能让模型看到，但语义混乱，无法独立校验，也不利于以后增加发布日期、适用型号和资料状态。项目使用独立字段 `documentReference`、`versionLabel`、`languageCode`，数据库查询失败时不调用模型。

## 为什么采用适配器而不是改数据库？

数据库已经正确保存来源身份和外键关系，问题发生在组件接口映射。改表不能解决字段未传递，反而会制造重复数据。适配器只补齐边界信息，旧证据门的权限、落库、幂等和风险规则全部复用。

## 成熟业务参考

Amazon Bedrock 的知识库引用包含具体来源文档、位置和引用内容；Azure AI Search 的检索结果也提供来源追踪、引用和执行元数据。它们说明企业知识问答不能只传一段裸文本。本项目采用同一原则，但实现和规模均为项目级，不能宣称等同于云产品。

## 问题与调整台账

- 现象：U301 首跑判无答案并安全转人工；
- 证据：数据库有 NVE41300，旧 `AnswerabilityCandidate` 没有资料身份字段；
- 根因：来源身份在证据门到判断器的接口映射中丢失；
- 被否决：调高 E5、提示词强制直接回答、把编号硬编码进标题；
- 调整：数据库回查适配器 + 第六版来源感知判断器；
- 复测：R284、R285 通过，真实 R286 通过；
- 边界：这是已暴露回归，不是新未见准确率。
