# 阶段二十九：展示站工作台与独立后端联调

## 30秒介绍

我把原来的命令行双分支演示封装成独立 HTTP 服务，并在个人作品集增加一页工业工单工作台。浏览器只选择“资料版本匹配”或“版本不匹配”，后端每次从零迁移 PGlite、调用正式业务工具并返回证据判断、工单终态和七类数据库计数。前端不放密钥、不伪造结果；正常路径形成一版方案并解决，来源不匹配路径内容模型零调用、方案零条并转人工。项目完整测试扩展到318项，最新为291通过、0失败、27项按登记跳过。

## 为什么不是把接口直接写在 Next.js 页面里

原展示站使用静态导出，发布物没有可执行的 Next.js 服务端。把动态 POST 接口写进页面会破坏当前部署方式；把结果写死又不能证明后端运行。因此采用“静态页面 + 独立 Node.js 服务”：页面负责交互，后端负责数据库、业务规则和证据。

## 高频问题

### 1. 网页究竟证明了什么？

它证明从浏览器请求到后端、迁移、数据库、业务工具和结果展示可以连通；不证明生产并发、真实工厂效果或公网高可用。

### 2. 为什么只允许两个预设场景？

这是作品集演示，不是公开维修问答产品。白名单能控制运行时间、成本和安全边界，也避免访客输入任意危险维修内容。若要开放自由输入，必须先补鉴权、限流、内容安全和数据隔离。

### 3. 为什么每次都创建新数据库？

演示目标是可重复和互不污染。新数据库保证每次计数来自本次请求，避免上一位访客或上一条分支残留数据。代价是启动更慢，也不代表生产数据库方案。

### 4. 怎样防止浏览器伪造成功？

页面没有内置结果和延时假动画，只在后端返回成功状态后渲染结果。后端不可用或返回结构错误时明确报错。接口测试还验证了来源限制、非法场景拒绝和浏览器预检。

### 5. 为什么需要跨域来源白名单？

前端和后端分别部署，浏览器会发送来源信息和预检请求。后端只给配置过的展示站来源返回允许头，降低其他网页直接滥用演示接口的风险；但来源白名单不是身份认证，公开自由输入时仍要鉴权和限流。

### 6. 哪些企业案例支持这个方向？

Spotify 的发布管理页面使用 React/TypeScript 前端和独立后端聚合多个系统；Shopify Hydrogen 用定制前端连接 Storefront API，并在内部产品生产使用。它们证明前后端分离和统一接口是成熟做法。本项目规模小得多，只借鉴职责划分，不借用它们的规模成绩。

### 7. 现在能说“上线”吗？

可以说“独立页面已进入原展示站，本地前后端联调通过，私有静态站可发布”。不能说“公网可运行后端已上线”，因为还没有选定公网 Node.js 托管地址，也没有正式 PostgreSQL、监控和备份。
