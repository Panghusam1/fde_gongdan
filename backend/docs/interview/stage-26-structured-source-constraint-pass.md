# 阶段二十六：结构化来源约束与第四批首次未见通过

## 30秒回答

连续三批未见题证明提示词不能充当资料身份安全边界后，我把原始问题、人工确认的内容问题和资料编号/版本/语言拆成独立字段。数据库先对最多五个候选做精确来源过滤：没有匹配就直接拒绝且不调用模型，有匹配只把匹配候选交给千问判断正文。第四批首次真实未见 11/12，五条无匹配来源全部程序拒绝，错误来源接收 0、判断错误 0。

## 2分钟回答

旧主链虽然把数据库来源字段传给模型，但用户仍能在自由文本里要求模型把中文资料当英文资料，第三批因此放行一条伪造语言来源。我没有继续补提示词，而是重新划分职责：资料编号、版本和语言是确定性的业务身份，交给程序；正文能否回答问题是语义任务，才交给模型。

新接口包含 `rawQuestion`、`confirmedContentQuestion` 和 `requestedSourceIdentity`。原始问题只用来核对确认记录是否属于同一次检索，永远不发给内容模型。数据库按编号、版本、语言精确筛选候选。没有匹配时返回固定拒绝，模型调用数为 0；有匹配时只发送过滤后的候选。第四版正式主链不再暴露可以绕过确认步骤的裸判断器。

我先用 R312—R316 把安全接口和主链契约写成失败测试，再实现；R317—R318 验证 12 条数据关系和模型调用次数；R319 对 17 个输入做首跑前散列封存；R320 连接真实千问。首跑 11/12，来源安全硬门全部通过。唯一 T707 是“部分相关”与“不能回答”的保守分类差异，原报告和原标签都保留。

```text
                                        │
确认的资料编号/版本/语言 ─→ 数据库过滤 ─┼─ 无匹配 → 程序拒绝 → 0次模型调用
                                        │
确认后的内容问题 ───────────────────────┴─ 有匹配 → 只判断匹配正文
```

## 设计全流程

1. **现象**：第六、七、八版提示词在已暴露题上能修复，但新表达继续失败；
2. **职责拆分**：来源身份要求确定一致，正文支持关系允许语义判断；
3. **备选比较**：继续补提示词被三轮证据否决；正则猜目标会误伤版本比较问题；最终采用人工确认结构化字段；
4. **数据库路径**：以最多五个命中主键为入口，连接资料版本后做三字段精确比较；
5. **接口防绕过**：原始问题不进入内容模型，正式主链不公开裸判断器；
6. **先测后写**：先看到模块不存在的红灯，再实现最小代码转绿；
7. **首跑封存**：题、代码、执行器和测试全部算散列，真实报告只创建一次；
8. **保留边界**：T707 不事后改标，项目题不冒充生产数据。

## 为什么没新增复合索引？

这条查询不是从全库扫描三字段，而是先拿最多五个 `knowledge_search_hits` 主键，再通过已有主键和外键连接。固定小集合下新增复合索引没有实际收益，还会增加写入维护成本。未来如果改成在全库向量召回前按来源筛选，访问路径变化，才需要用正式 PostgreSQL 的执行计划和真实数据量重新判断。

## 成熟做法与权威性

- [Amazon Bedrock Knowledge Bases RetrievalFilter](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_RetrievalFilter.html) 公开支持用元数据条件过滤检索结果；
- [Azure AI Search 向量过滤](https://learn.microsoft.com/zh-cn/azure/search/vector-search-filters) 公开说明过滤作用于可过滤的非向量字段，并可在向量检索前后执行。

它们由产品发布方维护，因此对“各自产品具备什么公开接口”是一手资料。它们只能作为架构参照，不能证明这些公司内部业务与本项目完全相同，也不能替代本项目自己的测试。

## 高频追问

### 为什么不把原始问题也发给模型？

因为前三批失败已经证明自由文本可以覆盖来源要求。内容模型只需要回答“正文是否支持这个内容问题”，不需要再次解释哪个版本才算目标。

### 人工确认是不是降低了系统价值？

不是让工程师手工写方案，而是让人确认一个高影响、低成本的身份字段。系统仍负责检索、证据判断、风险阻断、完整方案和全过程记录。把不可逆风险边界交给一次点击确认，是合理的人机分工。

### 11/12 为什么算通过？

门槛在真实运行前冻结为至少 11/12，同时错误来源接收必须为 0、判断错误必须为 0。本轮三项都达到。T707 是更保守拒答，不是危险放行；仍保留为后续内容分类改进项。

### 现在能宣称来源攻击全部解决吗？

不能。可以说项目自建第四批未见集上错误来源接收为 0。还没有系统红队、真实工厂输入和正式并发测试，不能外推为生产安全率。

## 简历可用表述

设计并实现工业知识工单的结构化来源安全门，将资料编号、版本和语言从自由文本提示中拆出，由 PostgreSQL 兼容数据库在模型调用前精确过滤；无匹配时零模型调用拒绝，有匹配时仅对可信候选执行语义判断。通过首跑前散列封存和真实千问未见测评达到 11/12，五条来源不匹配全部程序阻断，错误来源接收与判断异常均为 0。

面试展开时可以补充项目原则：“页面位置不能决定知识边界，业务目的和风险边界才能决定知识边界。”同样，文字里出现某个版本号也不能决定可信来源，来源身份必须由受信业务字段和数据库关系确定。
