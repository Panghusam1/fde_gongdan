# ATV320智能工单项目最终总结

## 项目状态

三天压缩计划中的本地工程任务已经完成：数据库与检索、协调助手与完整工单、扩展评测与安全重构、覆盖六阶段的13条多工单目录、五条可运行演示、项目说明、简历和面试材料均已落盘。这里的“完成”是本地可重复交付，不是生产部署。

仍待实施的工程事项：网络服务入口、正式 PostgreSQL + pgvector、容器发布、线上观测、备份恢复和小流量发布。仍依赖外部条件的事项：ATV320领域工程师审核、脱敏真实工单、生产环境权限，以及具有合法权限的二次排序服务密钥。

## 最终架构

```text
现场用户
  ↓
单协调助手 ──读取当前工单许可──→ 窄工具
  │                                  │
  │                                  ├─ 追加观察
  │                                  ├─ 官方资料检索
  │                                  ├─ 证据与来源判断
  │                                  ├─ 固定风险门
  │                                  ├─ 最多两版方案
  │                                  └─ 确认或人工接管
  │
  └─ 不直接修改数据库

结构化来源身份 → 数据库精确过滤 → 匹配正文 → 内容模型
                                  └→ 无匹配：零模型调用拒绝
```

## 关键决策与调整

1. **关系数据与向量数据共存**：工单、权限和版本关系存关系表；审核正文的向量单独版本化保存；
2. **页面不是知识边界**：以业务目的、产品适用性和风险切分片段，并保留跨页、多段精确来源；
3. **混合检索不因理论先进就上线**：40题证明当前融合首位73.3%低于E5的76.7%，因此不宣称改进；
4. **相似度阈值被留出集推翻**：0.86阈值无答案拒答83.3%、接收准确率84.6%，未接入主链；
5. **证据判断替代单阈值**：新36题总体97.2%、无答案拒答100%，再接入工单证据门；
6. **协调模型编号不可信**：端到端失败后由程序用数据库当前状态覆盖模型填写的内部编号；
7. **来源提示词不可信**：三批未见失败后改为人工确认结构化来源和数据库过滤；
8. **历史失败不可覆盖**：R291污染旧封存文件后被判失败，恢复旧散列并新增版本化实现。

## 成熟方案参考

- PostgreSQL/pgvector：关系数据、约束、事务和同库向量；
- E5研究与模型说明：查询和文档前缀、归一化语义向量；
- AWS Bedrock Knowledge Bases：用元数据 `RetrievalFilter` 过滤来源；
- Azure AI Search：向量检索前后对可过滤字段执行过滤；
- LangGraph、OpenAI Agents等工作流思想作为编排对照，但本项目根据业务选择单协调助手和程序状态机，没有为了使用框架而使用框架。

外部资料只证明发布方公开的能力与方法，不能替代项目自己的运行证据。

## 下一阶段怎样扩展成第二个独立项目

本项目的核心亮点是可信知识、数据库约束、检索和安全工作流。下一个简历项目不应只是增加一个故障码，而应换业务问题和核心难点，例如销售客户经营、企业战略研究或获客运营，同时复用三天流程：第一天数据与检索、第二天智能体与整体闭环、第三天未见评测、演示和简历交付。
