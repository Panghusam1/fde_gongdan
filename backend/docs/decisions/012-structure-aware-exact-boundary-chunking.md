# 设计决定 012：按手册结构切片并保存页内精确范围

- 日期：2026-08-18
- 状态：已通过测试实现
- 适用范围：知识候选生成、原文定位、审核门禁和协调助手工具权限

## 要解决的问题

一整页手册可能同时包含多个故障代码、阈值、复位条件和安全警告。只记录“第72页”仍然回答不了：

- 片段具体用了页面里的哪几个字；
- 模型有没有把自己的总结冒充成手册原文；
- 同一句出现两次时选的是哪一处；
- 一个安全警告有没有被拆掉标题、后果或限制条件；
- 同一页两段不相邻的证据怎样共同组成一个片段；
- 换了切片方法后能不能复现旧结果。

## 比较过的四种切法

| 方案 | 优点 | 在ATV320手册上的问题 | 结论 |
|---|---|---|---|
| 固定字数 | 实现快、长度整齐 | 可能从故障列表中间切开，也可能把“重启步骤”和紧随其后的警告拆开 | 不作主方法，只保留为超长内容的最后限长手段 |
| 一页一个片段 | 页码天然清楚 | 第72页有大量故障代码，检索OHF时会带入许多无关内容 | 淘汰 |
| 完全由模型按语义切 | 能理解自然语言 | 边界不稳定，模型可能改写或漏掉危险说明，难以复现 | 模型只能提议，不能直接批准 |
| 结构规则为主，长度为辅 | 保留故障条目、参数条目、警告框和步骤块，结果可复现 | 需要针对手册结构写规则并保留人工复核 | 采用 |

选择第四种，并允许协调助手提交候选边界。程序负责逐字核对，人工负责最终确认。

## 真实产品参照及适用边界

- [Amazon Bedrock 知识库的切片说明](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)在正式产品中同时提供固定长度、父子层级和语义切片，并明确保留片段到原文档的映射。这证明切法要按业务选择，不存在一个通吃的固定数字。
- [Microsoft Azure AI Search 的文档切片说明](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)列出固定长度、按标点或标题变化、语义切片和组合方案；[版面结构切片说明](https://learn.microsoft.com/en-us/azure/search/search-how-to-semantic-chunking)利用标题、段落和句子结构，并保存父级来源字段。
- [Docling 的切片说明](https://docling-project.github.io/docling/concepts/chunking/)先利用文档层级结构，再按嵌入模型可接受的长度做拆分或合并；过小片段只有在标题和说明相同等条件下才合并。

这些资料是对应产品或项目维护方的一手说明，权威范围是“这些产品公开支持什么能力”。它们不能证明本项目的具体字段、阈值或安全规则与其内部实现相同。

## 本项目的第一版切片规则

1. 一个故障代码条目单独成片，例如第72页 `OHF: 设备过热`，不带相邻错误代码。
2. 阈值条目把参数名称、数值、单位和触发含义保留在一起。
3. 复位条件必须同时说明“原因消失后才允许”以及OHF确实属于该复位列表；两段不相邻时保存两条精确来源。
4. 警告或危险块必须保留等级标题、危险后果、全部要求和后果说明，不能只截操作句。
5. 涉及断电、上锁、等待放电、直流母线测量、拆机或保护参数修改的片段标为工程师专用。
6. 原文没有危险标题时，不伪造“危险”等级；系统用途仍可因业务规则设为工程师专用。
7. 第一版不先定“每500字”之类的统一数值。等 E5 小模型接入后，再按它的实际输入上限和检索评测增加长度兜底。

## 页内范围怎样表示

`knowledge_chunk_sources` 新增：

- `start_character`：从1开始，包含该字符；
- `end_character`：从1开始，不包含该字符；
- `source_excerpt`：该范围内的逐字原文。

采用“左边包含、右边不包含”是因为长度可以直接写成 `end_character - start_character`。数据库使用 PostgreSQL 的 `substring` 从保存的页面正文重新截取并与 `source_excerpt` 比较。两者不同就拒绝写入。

[PostgreSQL 字符串函数](https://www.postgresql.org/docs/current/functions-string.html)明确说明 `substring` 按第几个字符和字符数量取值；[PostgreSQL 约束说明](https://www.postgresql.org/docs/current/ddl-constraints.html)说明普通检查约束不应读取其他表，因此本项目用行内检查约束校验范围形状，用触发器对照页面提取表。

## 切片方式为什么要记录版本

`knowledge_chunks` 新增：

- `chunking_method`：人工选择、结构规则或模型提议；
- `chunker_name`：哪个程序或审核界面产生边界；
- `chunker_version`：具体版本。

迁移前的待审核旧片段统一标成 `legacy_unversioned`，但这种历史片段不能审核通过。数据库拒绝没有工具名称和版本的正式切片通过审核。

## 候选创建服务的权限边界

协调助手不能提交 `original_text`。它只能提交：

- 资料版本；
- 页面提取结果编号；
- 想截取的逐字原文；
- 内容分类、危险等级和用途建议；
- 切片工具名称与版本。

服务按顺序执行：

```text
核对页面属于指定资料版本
  → 核对页面提取成功
  → 在页面中查找逐字摘录
  → 找不到则拒绝
  → 出现多次则拒绝猜位置
  → 计算页内起止位置
  → 按来源顺序拼出机器原文
  → 在一个事务中写入待审核片段和全部来源
```

服务永远创建 `unreviewed`，没有直接批准参数。人工审核是另一项权限。

## 实施时发现并修正的结构问题

迁移 013 原先规定“同一提取结果不能重复挂到一个片段”。有了精确范围后发现，第310页的“复位前提”和“OHF属于可复位列表”不相邻，却应共同构成证据。

因此唯一规则改为：同一片段、同一提取结果、同一起点和同一终点不能重复；同一页的两个不同范围可以并存。原来的 R84 重复范围测试仍然通过，同时新增 R111 证明两个不同范围能够成功写入。

## 迁移策略

旧来源关系没有页内范围，数据库不能可靠判断应选择页面中的哪一段。迁移 014 遇到任何旧来源关系都会明确阻断，要求先做人工边界回填，不能用字符串首次出现位置自动猜测。

没有来源关系的旧待审核片段可以迁移，但会标为无版本历史切片，不能直接通过审核。

## 真实资料产物

第一版候选包包含6组、8条精确来源：

1. OHF故障定义；
2. OHF热状态阈值；
3. OHF手动复位条件和适用列表；
4. 产品重启的“未预期设备运行”警告；
5. 禁用错误检测的完整危险块和OHF适用列表；
6. 不可复位错误的断电、上锁、放电和测量步骤。

它们全部保持待审核。第50页已知有 `1 18%` 的基础提取问题，尤其不能由程序自动批准。

## 代价和仍未完成的部分

- 手工选择的第一批片段数量少，但用于验证规则，不冒充整本440页已经完成切片。

- 还没有接入 E5 小模型，因此没有最终长度上限、向量和检索效果数据。
