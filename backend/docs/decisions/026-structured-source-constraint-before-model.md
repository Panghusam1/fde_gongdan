# 决策026：来源身份改为模型调用前的结构化约束

## 状态

已实施并通过第四批首次真实未见能力门。第四版正式主链要求结构化来源确认，数据库先精确过滤，原始自由文本不进入内容判断模型。R320 首跑 11/12，五条无精确来源均由程序拒绝，错误来源接收 0、判断错误 0。

## 备选方案

### 方案一：继续加强提示词

优点是改动小。缺点是三批未见数据已经证明新表达仍能绕过，而且无法给出确定性安全保证。否决。

### 方案二：只用正则从用户问题提取编号、版本和语言

优点是执行快、可测试。缺点是正常比较问题可能同时出现多个版本或语言，程序无法仅凭词面确定目标。可用于检测“文本里出现了来源身份”，不能作为唯一真值来源。

### 方案三：用户确认结构化来源，程序过滤，模型判断正文

采用。来源编号、版本、语言由界面选择、上一步确认或受信业务字段传入；程序对数据库做精确过滤，模型看不到不符合约束的候选。

```text
自由文本问题 + 已确认来源身份
              ↓
程序校验编号、版本、语言
       ├─ 0条：补充或重新确认，不调用模型
       └─ ≥1条：只保留匹配候选
                         ↓
                 模型逐候选判断正文
                         ↓
              直接回答 / 部分相关 / 无答案
```

代价是交互多一步，接口和工单上下文要增加结构化字段；收益是来源身份不再受提示注入、措辞变化或模型波动控制。

## 最终实现

- `rawQuestion`：保存并核对本次检索问题，只用于防止确认结果错绑到另一轮检索，不发送给内容模型；
- `confirmedContentQuestion`：人工确认后的纯内容问题，发送给模型；
- `requestedSourceIdentity`：独立保存资料编号、版本和语言；
- 数据库用大小写不敏感的精确比较筛选最多五个候选；
- 无匹配返回程序拒绝，模型调用数为 0；有匹配时只把匹配候选交给第八版逐候选判断器；
- 第四版主链不再公开可绕过确认步骤的裸判断器。

本轮没有新增复合索引。查询先用最多五个 `knowledge_search_hits` 主键定位，再通过已有主键和外键连接来源表；对这种固定小集合访问，新增三字段索引没有实际收益。若未来把来源过滤前移到全库向量召回之前，必须再用正式 PostgreSQL 的 `EXPLAIN (ANALYZE, BUFFERS)` 根据真实数据量决定索引。

## 成熟产品参考

- Amazon Bedrock Knowledge Bases 的 `RetrievalFilter` 使用元数据键值和 `equals`、`in` 等确定性条件筛选可返回的数据源，而不是让生成模型决定是否忽略这些字段：[AWS API 文档](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_RetrievalFilter.html)。
- Azure AI Search 明确让过滤表达式作用于可过滤的非向量字段，并支持在向量检索前后执行过滤：[Azure AI Search 文档](https://learn.microsoft.com/en-us/azure/search/vector-search-filters)。

这些是 AWS 和 Microsoft 维护的产品接口文档，对“各自产品公开支持什么能力”具有一手权威性；它们不能证明本项目已经达到相同成熟度，也不能证明某个客户的内部实现。

## 为什么适合当前业务

本项目的资料编号、版本、语言已经存于关系数据库，且错误版本可能改变维修依据。它们是确定性业务边界，适合程序过滤；正文是否足以回答现场问题具有语义性，适合模型判断。这个分工与当前数据结构一致，也能把错误来源接受数变成可确定测试的 `0`。

T707 的候选只说明风机与热状态相关，预标为“部分相关”，真实模型更保守地判为“不能回答”。该差异保留为内容分类边界，不影响来源安全门，也不事后改标签提高首跑分数。
