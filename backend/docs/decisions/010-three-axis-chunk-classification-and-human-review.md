# 设计决定 010：知识片段采用三维分类和人工审核

- 日期：2026-08-18
- 状态：已通过测试实现
- 适用范围：知识片段进入检索系统前的分类、核对和放行

## 要解决的问题

旧表只有一个自由文字字段 `risk_label`。它把三个不同问题混在了一起：

1. 这段内容讲的是什么；
2. 官方资料自己标注的危险程度是什么；
3. 我们的系统允许把它用到哪里。

例如，“危险：断电后等待 15 分钟”既包含安全警示，也包含操作条件。只写一个“高风险”无法告诉程序：它能不能展示给用户、能不能生成操作步骤、是否必须转工程师。自由文字还允许模型随意写出“有点危险”“大概安全”等无法统一处理的值。

## 考虑过的方案

### 方案一：仍保留一个风险标签，由模型自由填写

优点是字段少。缺点是含义混杂、无法稳定筛选，也无法阻止模型把“危险原文”同时标成“低风险指导”。不采用。

### 方案二：全部分类和正文都由工程师从零录入

优点是控制严格。缺点是人工成本高，模型只剩一个资料展示器，不能发挥提取、候选分类和整理能力。不采用。

### 方案三：模型提出完整候选，人核对后一次确认

模型可以先提出内容种类、原文危险等级、系统用途和整理后的正文。审核人对照官方页面，修改或确认后提交。数据库要求任何“已通过”记录必须同时留下审核人、时间、核对正文和理由。

选择方案三。它符合本项目已经确定的原则：模型负责准备完整方案，人负责现实世界确认，程序和数据库负责不可绕过的底线。

## 三个维度

### 维度一：内容种类

回答“这是什么内容”：

| 程序值 | 中文含义 |
|---|---|
| `unclassified` | 待分类 |
| `fault_definition` | 故障定义 |
| `threshold` | 数值阈值 |
| `reset_condition` | 复位条件 |
| `procedure` | 处理步骤 |
| `diagnostic_context` | 诊断依据 |
| `safety_warning` | 安全警示 |
| `restricted_setting` | 限制性参数或设置 |

### 维度二：资料原文的危险等级

回答“发布方原文怎样标注”：

| 程序值 | 中文含义 |
|---|---|
| `unclassified` | 尚未确认 |
| `information` | 普通说明，没有安全标题 |
| `notice` | 注意，通常指与人身伤害无关的危害 |
| `caution` | 小心，可能造成轻微或中度人身伤害 |
| `warning` | 警告，可能造成严重伤害或死亡 |
| `danger` | 危险，不避免将造成严重伤害或死亡 |

这不是模型自己估计危险程度，而是记录官方资料的原始标识。施耐德 NVE41300 的 PDF 第 5 页明确解释了“危险、警告、小心、注意”的区别，因此本项目按资料自身定义保存，而不是自己发明等级。

### 维度三：系统允许用途

回答“我们的助手能怎么用”：

| 程序值 | 中文含义 |
|---|---|
| `reference_only` | 仅作事实回答和证据引用 |
| `low_risk_guidance` | 可进入给现场用户的低风险方案 |
| `engineer_only` | 只能用于人工工程师交接 |

资料标成“小心、警告或危险”时，不允许同时标成“低风险指导”。它仍可作为证据展示，或用于告诉工程师为什么系统停止自动处理。

## 为什么保留机器原文和核对正文

真实手册第 50 页肉眼显示 `118%`，pypdf 基础提取却可能得到 `1 18%`。数字之间多一个空格，在普通文章里影响不大，在设备阈值里却可能改变检索和判断。

因此同时保存：

- `original_text`：机器当时提取或切分得到的原始内容；
- `verified_text`：审核人对照官方页面后确认可用的正文；
- `review_notes`：为什么通过、修正或驳回。

不能覆盖原始内容，因为覆盖后无法复查提取错误；也不能只用机器原文，因为已发现真实数字错误。

## 谁负责提出，谁负责确认

- 协调助手：读取手册和受控规则，提出完整分类、用途和正文建议；
- 程序与数据库：验证来源、字段组合、状态和权限是否合规，但不判断设备维修含义；
- 领域工程师：确认、修改或驳回设备含义与安全用途；
- FDE：设计上述数据结构、审核流程、权限隔离、审计记录和自动化测试，不承担变频器专业结论。

因此，候选文件里的分类值都表示“等待专业审核的建议”，不能在材料里写成已被设备工程师确认的事实。

## 审核状态和数据库规则

审核状态只有三种：待审核、已通过、已驳回。

- 待审核：不能带审核人、审核时间、核对正文和审核理由；
- 已通过：内容种类和危险等级必须完成分类，必须有非空核对正文、真实审核人、审核时间和理由；
- 已驳回：必须有真实审核人、审核时间和理由，不能留下伪装成可用内容的核对正文；
- 审核人通过外键连接系统用户，不能填一个不存在的编号；
- 旧数据升级后默认为“待分类、待审核、仅供查阅”，不会自动放行；
- 旧 `risk_label` 政名为 `legacy_risk_label`，数据保留，但新代码不再把它当正式字段使用。

这些规则由迁移 `012_classify_and_review_knowledge_chunks.sql` 和 R67—R77 测试实现。

## 为什么使用数据库检查而不只在提示词中要求

提示词只影响某一次模型输出；数据库可能同时被导入脚本、后台任务、接口和人工工具写入。PostgreSQL 的检查约束会在插入或更新时拒绝不符合当前行逻辑的值，外键保证审核人真实存在。因此“危险资料不能作为低风险指导”和“审核通过必须有完整留痕”放在数据库最后一道门。

数据库仍不能证明审核人具备设备维修资质，也不能证明正文工程含义一定正确。人员权限、审核界面和专业复核还需要应用层与组织制度共同保证。

## 真实产品和权威资料参照

- [施耐德电气 NVE41300 官方页面](https://www.schneider-electric.cn/zh/download/document/NVE41300/)确认文件编号、中文 05 版、适用产品和维护诊断用途；具体安全等级来自该官方 PDF 第 5 页。发布方是设备制造商，因此对该产品手册内容是一手来源，但不能替代厂区制度和法规。
- [IBM watsonx Orchestrate 文档提取器](https://www.ibm.com/docs/en/watsonx/watson-orchestrate/base?topic=workflows-adding-document-extractors)在文档提取可信度不足或结果为空时创建用户复核任务，复核人可以对照原文修改提取值；其评测资料也要求由人确认正确值后再计算准确率。这证明“机器先提取、人核对后继续流程”是实际企业产品能力。
- [Microsoft Document Intelligence 透明度说明](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/document-intelligence/transparency-note)要求用代表真实业务的数据做试验，并建议高风险场景保留人工监督。文中的 0.80 只是示例，不是本项目可照抄的行业阈值。
- [PostgreSQL 官方约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html)规定检查约束可以校验同一行的多字段组合，外键用于维护跨表引用完整性。这是本次字段组合检查和审核人外键的直接技术依据。
