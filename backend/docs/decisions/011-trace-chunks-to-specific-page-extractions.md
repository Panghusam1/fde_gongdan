# 设计决定 011：知识片段必须连接具体页面提取结果

- 日期：2026-08-18
- 状态：已通过测试实现
- 适用范围：知识片段来源追踪、审核门禁和审核后证据冻结

## 要解决的问题

迁移 012 让知识片段具备三维分类和人工审核，但旧字段 `page_number` 只能说明大概来自第几页，不能回答：

- 来自 pypdf、Docling、光学识别还是人工录入；
- 使用的是哪个工具版本和配置；
- 一个跨页片段按什么顺序连接多个来源；
- 片段审核通过后，来源或提取正文有没有被换掉；
- 片段所声明的资料版本是否与页面真实版本一致。

如果这些问题不能回答，所谓“引用官方手册”仍只是文字声明，不是可以回查的数据关系。

## 考虑过的三种方案

### 方案一：知识片段只保存资料版本和页码

优点是结构简单。缺点是同一页可以有多种提取结果，页码无法指明采用了哪一种，也无法恢复当时使用的工具版本。淘汰。

### 方案二：知识片段直接保存一个页面提取结果编号

优点是查询简单，能够精确到提取结果。缺点是一条片段只能连接一个来源，无法自然处理跨页段落，也无法给多个来源排序。适合明确禁止跨页切片的小系统，不适合当前长期结构。

### 方案三：建立独立的片段来源关系表

一个知识片段可以连接一条或多条具体页面提取结果，并用 `source_order` 记录顺序。代价是多一张表和几组外键，但可以支持跨页内容、不同提取工具对照和以后重切片。

选择方案三。

## 数据关系

```mermaid
flowchart LR
    A["逻辑资料"] --> B["具体资料版本"]
    B --> C["PDF页面身份"]
    C --> D["具体提取结果"]
    D --> E["片段来源关系"]
    E --> F["知识片段"]
```

新增表 `knowledge_chunk_sources` 的关键字段：

- `knowledge_chunk_id`：哪一个片段；
- `source_version_id`：片段和页面共同所属的资料版本；
- `document_page_id`：哪个 PDF 页面；
- `page_extraction_id`：该页的哪一次工具结果；
- `source_order`：多个来源的拼接顺序。

## 为什么关系表重复保存版本和页面编号

仅保存 `knowledge_chunk_id` 和 `page_extraction_id`，查询时也能沿关系找到版本和页面。但数据库无法用普通外键直接保证两条远端关系属于同一版本。

因此关系表有意重复保存版本和页面编号，再用三层组合外键锁死：

1. “片段编号 + 资料版本”必须是知识片段表中的真实组合；
2. “页面编号 + 资料版本”必须是页面表中的真实组合；
3. “提取结果编号 + 页面编号”必须是提取结果表中的真实组合。

这种重复是受约束的冗余，用来让数据库直接拒绝05版片段接04版页面、或第72页接第50页提取结果。它不是让多份数据各自自由变化。

## 审核门禁

知识片段的正确创建顺序固定为：

```text
建立待审核候选
  → 绑定一条或多条具体来源
  → 人工核对分类和正文
  → 更新为已通过
```

数据库触发器会拒绝没有任何来源关系的“已通过”记录。不能直接插入一条已通过片段，因为片段尚不存在时也不可能先建立来源关系。

普通检查约束不能读取另一张表。PostgreSQL 官方建议跨表完整性优先使用外键，需要在写入时检查其他行时使用触发器，因此本项目用组合外键保证身份关系，用触发器保证“至少存在一个来源”。

## 为什么审核后冻结

来源编号不变，不代表证据内容不变。如果 `page_extractions` 可以原地修改，片段仍指向同一编号，但审核人当时核对的文字已经被替换。

迁移 013 因此规定：

- 页面提取结果只能新增，不能更新或删除；
- 待审核片段及其来源可以调整；
- 片段一旦通过或驳回，片段正文、分类和审核信息不能更新或删除；
- 片段一旦通过或驳回，其来源关系也不能新增、更新或删除；
- 发现错误时新建候选重新审核，不覆盖历史。

这样旧工单可以还原当时引用的知识和工具结果。

## 旧数据迁移策略

触发器只检查未来写入，不会自动验证旧记录。迁移 013 在创建新表之前先检查旧库：只要存在没有具体来源关系的已通过片段，就阻断迁移并报告原因。

不选择自动猜页码，也不悄悄把旧片段改回待审核，因为两种做法都会改变已有审核事实。当前项目尚无正式已通过知识，因此可以安全升级；未来真实升级需要先制定来源回填清单。

## 真实数据验证

测试 R90 导入真实的 440 页 NVE41300 提取文件，定位：

- PDF 第 72 页；
- `pypdf 6.10.0`；
- 页面文字指纹 `e8e2fddc584251547b8364c8a25faeba2058a5ea6cc1b13fefb42a0e231d9056`；
- 原文包含 `[设备过热] OHF: 设备过热`。

随后建立 OHF 故障定义片段、绑定该提取结果并完成人工审核，最终可以从片段反查页码、工具、版本和审核状态。

## 真实产品参照

- [Microsoft Azure AI Search 的版面切片说明](https://learn.microsoft.com/en-us/azure/search/search-how-to-semantic-chunking)明确要求搜索索引中的片段带一个父级字段，用来识别片段来源。它证明“片段不能脱离父级来源”是实际搜索产品设计；本项目进一步追踪到页面提取版本。
- [Google Cloud Document AI 的 Document 结构](https://docs.cloud.google.com/document-ai/docs/reference/rest/v1/Document)保存文档修订关系，并区分修改来自人员还是处理器。它证明“机器加工版本、人工作业和父级修订要可追踪”是实际文档产品设计。
- [IBM watsonx Orchestrate 文档提取器](https://www.ibm.com/docs/en/watsonx/watson-orchestrate/base?topic=workflows-adding-document-extractors)让审核人在文档查看器中对照源文档检查提取值，验证后流程才继续。它证明审核界面需要把结果和来源放在一起。
- [PostgreSQL 约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html)是组合外键和跨表检查边界的直接技术依据；[触发器文档](https://www.postgresql.org/docs/current/trigger-definition.html)说明触发器在写入前后的执行方式。

外部产品只证明设计思想有实际背景，不代表这些公司使用了本项目完全相同的表结构和审核规则。
