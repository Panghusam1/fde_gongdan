# 设计决定015：工单范围内的官方资料检索工具与不可变审计

- 日期：2026-08-18
- 状态：已实现并通过专项测试
- 适用范围：协调助手在具体工单中检索官方知识

## 问题

检索算法已经能按产品族返回知识，但它仍只是内部函数。若直接把数据库、产品族编号或通用搜索接口交给AI，会出现四个问题：

1. AI可以伪造产品族编号，查询当前设备不适用的资料；
2. 提示词中的权限说明不是强制授权，越权请求仍可能进入数据库；
3. 工单只留下AI最后的回答，无法证明它当时查过什么；
4. 返回一段文字却没有资料编号、版本、页码和逐字摘录，不能叫可核验证据。

## 备选方案

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| 给AI通用SQL工具 | 最灵活 | 权限和查询范围几乎无法控制，提示注入影响直接进入数据库 | 拒绝 |
| 让AI传产品族编号调用通用检索 | 接口简单 | 模型可以传错或被诱导传入其他产品族 | 拒绝 |
| 只按当前用户过滤，不绑定工单 | 能阻止部分越权 | 无法证明检索针对哪台设备，工单过程不完整 | 拒绝 |
| 工单范围窄工具 | 输入少、范围可推导、可审计 | 服务和表结构更多，需要处理幂等和并发变化 | 采用 |

## 工具契约

协调助手可提供：

- 工单编号；
- 当前登录会话注入的厂区成员编号；
- 检索问题；
- 返回数量；
- 幂等键。

协调助手不能提供：

- 厂区编号；
- 设备编号；
- 规范型号编号；
- 产品族编号；
- 资料版本编号；
- 任意SQL。

程序沿以下关系自动推导范围：

```text
工单
  → 工单所属厂区
  → 现场设备
  → 规范型号
  → 规范产品族
  → 当前有效资料版本
  → 已审核知识
```

## 为什么登录成员编号仍然出现在工具输入中

当前TypeScript服务尚未接入真实HTTP身份中间件，因此函数需要一个`requesterMembershipId`表示可信会话边界。正式接口必须由登录会话注入，不能让模型从用户文字中提取或自由填写。

工具会同时验证成员和用户账号都启用，并且成员属于工单厂区。其他厂区成员、停用成员和停用用户都在模型调用前被拒绝，避免无意义的模型费用。

## 为什么模型推理在事务外

向量计算可能耗时或失败。若先锁定工单再等待模型，其他操作会长期阻塞。

实际流程是：

1. 第一次读取并验证工单、成员、设备、型号和产品族；
2. 在事务外计算查询向量并完成检索；
3. 开启短事务；
4. 重新验证权限和设备范围没有变化；
5. 批量保存检索运行、命中记录和工单事件；
6. 任一步失败则整笔回滚，不向AI返回未留痕结果。

这解决了“计算期间成员被停用或设备关联变化”的时间差问题。

## 审计表为什么分两层

### `knowledge_search_runs`

保存一次检索的上下文：工单、厂区、设备、规范型号、产品族、请求成员、问题、返回数量、模型版本、向量维度、分词器版本、融合策略、关键词是否实际参与和幂等键。

### `knowledge_search_hits`

保存每条结果：知识片段、最终名次、原始关键词名次与分数、原始向量名次与相似度、融合分数。

两张表分开后，一次检索可以有0到多条结果；零结果不是异常，而是“当前有效资料中没有证据”的正式业务事实。

## 为什么还要写工单事件

专门的检索表适合复盘算法，`work_order_events`适合展示完整工单时间线。因此一次成功记录的检索还会追加`knowledge_searched`事件，并关联具体检索运行。检索运行、命中和事件在同一事务中写入。

## 为什么审计记录不可修改

如果检索后可以改问题、名次或证据，就无法解释AI当时为什么给出某个建议。检索运行和命中记录只能追加，数据库触发器拒绝更新和删除。

知识片段本身在审核后也不可原地修改，命中记录关联片段即可回查当时的正式正文和来源链。

## 为什么要有幂等键

Agent调用、网页请求和网络代理都可能重试。没有幂等控制，同一个动作会重复计算模型、重复保存事件并污染统计。

同一工单、同一幂等键、完全相同的请求会直接返回已保存结果，不再次调用模型；同一幂等键换问题或模型则拒绝，防止把不同操作错误合并。

## 一条正式证据包含什么

- 发布方；
- 资料标题和编号；
- 官方网址；
- 版本标签和语言；
- 原文件SHA-256；
- PDF页码；
- 页内起止字符；
- 逐字摘录；
- 该摘录在片段中的顺序。

工具不会只返回AI摘要。协调助手后续可以整理这些证据，但引用必须保留可回查字段。

## 资料版本门禁

正式检索同时要求：

- 知识片段状态为`approved`；
- 所属资料版本状态为`current`；
- 产品族与工单设备一致；
- 向量模型和维度与本次查询一致。

资料版本变为`superseded`或`withdrawn`后，即使片段以前通过审核，也不能再返回。零结果检索仍然留痕。

## 数据库约束

迁移018使用复合外键同时固定：

- 检索运行中的工单、厂区和设备必须属于同一组关系；
- 设备、厂区和规范型号必须吻合；
- 规范型号必须属于记录的产品族；
- 请求成员必须属于该厂区；
- 工单事件只能关联一条真实检索运行。

这不是只依赖TypeScript“拼对几个编号”。即使将来增加另一个写入口，数据库也会拒绝矛盾范围。

## 真实产品与安全依据

- [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)把API、Lambda和现有服务转换成受治理的Agent工具，并提供进出站认证、凭据交换和审计能力。它证明企业Agent平台采用“定义工具接口并在网关执行认证”，不证明本项目必须部署在AWS。
- [AgentCore Gateway工作流](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-building.html)要求先定义OpenAPI或函数工具，再配置进站与出站授权。这与本项目“AI只看窄工具、业务服务执行授权”的职责分工一致。
- [OWASP LLM06:2025 Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)把功能过多、权限过大和自主性过强列为Agent风险，并建议最小工具、最小权限、在用户上下文中执行和由下游系统完整验权。
- [PostgreSQL约束官方文档](https://www.postgresql.org/docs/current/ddl-constraints.html)说明复合外键如何维持跨列关系完整性。

上述资料证明窄工具、下游验权和复合外键具有正式产品与安全依据。本项目的字段、状态范围、幂等规则和审计表仍是针对工业工单作出的设计。

## 当前边界

- 当前是本地PGlite验证，尚未为生产PostgreSQL创建独立最小权限数据库角色；
- 登录成员编号尚未由真实身份中间件注入；
- 还没有资料版本发布/撤回的正式审批服务；
- 工具目前只允许草稿、调查中和等待补充信息三种状态；
- 已完成检索和留痕，尚未接入风险判断与方案生成。
