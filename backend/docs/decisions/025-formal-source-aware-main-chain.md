# 决策025：用唯一正式组装入口固定第六版来源判断主链

## 状态

已实现并完成受控整链与真实模型升级回归。十二条数据已经暴露，因此本轮是回归，不是新的未见准确率。

## 触发问题

U301 专项回归已经证明：数据库补齐资料编号、版本和语言后，第六版判断器能够正确使用来源身份。但代码检查发现：

- 第六版判断器和数据库来源适配器只在专项测试中手工组合；
- 三套端到端入口仍显式创建第五版判断器；
- 通用协调函数允许调用者注入任意判断器；
- 因此“组件已经修好”不等于“正式业务一定使用修复后的组件”。

根因是缺少唯一正式组装入口，造成测试配置与业务配置可能漂移。

## 备选方案

| 方案 | 优点 | 缺点 | 决定 |
|---|---|---|---|
| 逐个脚本把第五版改成第六版 | 修改直接 | 新脚本仍可能忘记包装数据库来源身份，无法集中阻断回退 | 否决 |
| 删除第五版及旧入口 | 表面上最彻底 | 破坏旧首跑报告的可复现性，也不利于受控单元测试 | 否决 |
| 唯一正式主链工厂，旧入口只保留历史与底层测试 | 正式运行固定版本，同时保留历史复现和依赖注入 | 多一层组装代码，需要单独合同测试 | 采用 |

## 决策

新增 `src/coordinator/work-order-main-chain.ts`：

```text
正式环境配置
→ 第三版状态绑定协调模型
→ 第六版来源感知判断模型
→ 数据库来源身份适配器
→ 固定检索模型
→ 第二版状态绑定工单主循环
```

正式工厂有三项不可变条件：

1. 判断提示版本必须是 `answerability-v6-source-aware`；
2. 候选的资料编号、版本和语言必须由数据库来源链补齐；
3. 协调模型、检索器和判断器由工厂注入主循环，调用者不能在单次运行中替换。

第五版仍保留，只用于复现历史评测和隔离测试；正式主链传入第五版会在启动阶段被拒绝。

## 验证证据

- R288：正式环境入口的两次判断请求都收到数据库资料编号、版本和语言；
- R289：受控组装入口传入第五版会立即失败；
- R290：受控模型下十二条真实数据库工单终态 12/12，安全 5/5，危险误方案 0，判断错误 0；
- R291：业务结果为 12/12，但全量测试发现它修改了历史封存执行器，造成三条旧证据链失败，因此整轮按失败保留；
- R292：恢复旧执行器并新增独立来源感知执行器后，固定 E5、真实千问和真实数据库纠正回归 12/12，安全 5/5，危险误方案 0，判断错误 0，运行约 176.2 秒。

## 证据权威边界

这是由本项目代码审计和自动化测试推动的工程决定，不包装成某家企业的公开标准。目前没有核验到成熟企业公开披露与本项目完全相同的内部组装文件，因此不声称“某公司也这样接”。R291 还证明版本化本身是证据要求：新能力不能通过改写旧封存文件上线。

模型发布方资料只能证明结构化调用能力，不能证明本项目已经正确接入；真正支持本决定的是 R288—R291 的代码与数据库终态证据。

## 代价和重评条件

- 增加一个正式组装层和对应测试；
- 第六版继承第五版两阶段调用，普通可回答问题通常需要两次判断请求；
- 旧脚本仍可直接使用第五版，但不得作为正式业务入口；
- 若未来更换模型或提示版本，必须新建版本、修改正式工厂、重新跑受控整链、已暴露回归和新未见能力门。
