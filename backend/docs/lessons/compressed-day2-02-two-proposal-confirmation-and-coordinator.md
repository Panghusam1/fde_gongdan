# 三天计划第二天第二节：两版方案、现场确认和协调助手

## 这一节最终做出了什么

现在系统能够自动走完五条业务路径：

```text
普通问题 → 检索 → 低风险 → 第一版方案 → 用户确认恢复
第一版失败 → 新检索和新证据 → 第二版方案 → 用户确认恢复
第二版失败 → 人工接管
高危证据 → 人工接管，不生成方案
没有有效证据 → 人工接管，不凭常识猜测
```

用户得到的不是一句散文答案，而是一份包含事实、假设、步骤、停止条件和预期观察的完整方案。每份方案能追到具体检索、风险判断和资料片段。

## 协调助手到底做什么

协调助手只做一件事：结合用户当前话语和工单上下文，从程序给出的允许动作中选下一步并填写参数。

它不负责决定自己有没有权限，不负责放宽风险，不直接改数据库，也不能宣布设备已经恢复。现场用户的实际结果或工程师接管才会改变这些业务事实。

## 为什么不用多个助手

当前所有步骤围绕同一个工单按顺序发生，没有适合并行展开的独立任务。拆成检索助手、风险助手、方案助手会增加上下文传递和责任边界，却不会缩短关键路径。

单协调助手不是“整个系统只有一个提示词”。协调助手下面有多个窄工具，工具下面还有数据库约束和固定规则。系统复杂度被放在可测试的程序边界中，而不是堆在助手数量上。

## 为什么第二版不能只是换个说法

第一版失败说明原有信息不足或原推断不成立。若第二版继续使用相同现场反馈和相同知识片段，只是重新措辞，本质是重复猜测。

因此第二版需要三种可验证变化：失败后的实际结果、新的检索运行、至少一条新的底层知识片段。内容摘要也必须不同。缺一项就不能创建第二版。

## 本阶段三个真实故障

### 1. 错误原因被状态检查遮住

高危风险判断已经把工单转成等待人工。方案工具最初先检查工单状态，返回“状态不允许”，掩盖了真正原因“风险判断不允许方案”。调整为先核验风险结论，再检查状态，使审计和报错指向根因。

### 2. 一次取5条导致普通流程误阻断

测试中普通查询最相关的是低风险外部观察，但前5条还包含相似度很低的高危警告。风险门按整个证据集合保守判断，于是正常路径进入人工。

没有删除高危规则，也没有让模型忽略危险证据；而是把首轮证据集合缩到最相关1条，失败后再扩大到2条寻找新增证据，并把参数标记为第三天必须用扩展题库重测的实验值。

### 3. 新检索错配旧风险判断

第一版失败后完成了第二次检索，但“最近风险判断”仍属于第一次检索。许可表只检查旧判断是低风险，就过早允许生成第二版。方案工具通过复合关系发现新命中与旧判断不属于同一检索并拒绝。

修复不是放宽方案工具，而是让许可表先检查`risk.searchRunId === latestSearch.searchRunId`。只有因果血缘一致才能生成方案。

### 4. 固定快照在资源包地址返回404

配置文件中的密钥和资源包地址最初配合固定快照`qwen3.7-plus-2026-05-26`调用，网络已经连通但返回HTTP 404。使用同一密钥、同一地址，换成配置原本声明的`qwen3.7-plus`后返回200，证明问题是资源包不接受该快照名，而不是凭感觉怀疑密钥。

运行时因此支持项目专用模型变量，并兼容已有配置的模型名。当前真实调用使用滚动别名，同时明确记录可复现性代价；没有把404简单包装成“模型不可用”。

## 你应该记住

1. 模型负责提出动作，程序负责允许动作，数据库负责守住事实。
2. 方案不是聊天文字，而是有版本、有字段、有证据的业务对象。
3. 用户确认的是现场实际结果，不是“AI答案看起来不错”。
4. 第二版必须有失败反馈、新检索和新证据，不能只换措辞。
5. 最新记录不一定属于同一条业务链，必须比较关联编号。
6. 风险规则不能为了测试通过而放宽；应先检查检索集合是否合理。
7. 官方文档证明能力，企业案例证明使用方式，项目测试才证明当前适配性。
8. 当前是单协调助手加窄工具；只有出现可并行、独立的业务单元时才考虑多助手。
9. API接通不等于Agent有效；至少要分别验证地址、模型名、输出契约和业务轨迹。

## 当前边界

- 真实千问已通过检索动作和完整方案两项基础测试，但还没有完成大规模、多轮Agent轨迹评测；
- 五条E2E使用确定性的场景模型，证明编排和约束；两项真实模型测试仍不足以代表生产生成质量；
- 检索条数1/2是小题库下的暂定参数，第三天要用至少40题重新评估；
- 当前知识候选仍缺真实领域工程师批准，不能宣传为生产维修结论。
