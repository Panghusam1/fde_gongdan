# 第一天第 6 课：Docling、OCR 与受控智能工单

## 一句话记忆

- OCR：看图识字。
- Docling：把整份文档整理成有结构、能追溯的资料。
- 协调助手：理解人话、整理证据、草拟方案。
- 状态机：决定当前到底允许做什么。
- 窄权限工具：只开放完成某项任务所需的最小操作。
- 数据库：保存业务事实和完整历史。

## 1. OCR 和 Docling 的区别

### 1.1 OCR 解决的问题

扫描 PDF 的每一页本质上是一张图片。OCR 把图片中的字识别出来，例如：

```text
页面图片中的像素 → “OHF 变频器过热”
```

OCR 可能同时返回文字位置和可信度，但它通常不知道：

- 这一行是不是标题；
- 两栏文字应该先读哪一栏；
- 哪一段警告约束后面的哪些操作；
- 表格的行、列和合并单元格是什么；
- 页眉页脚是不是正文。

OCR 常见错误包括 `0/O`、`1/I` 混淆、故障码识别错误和中文漏字。工业场景中，一个故障码识别错误就可能检索到错误资料，所以关键型号和故障码必须另做质量检查。

### 1.2 Docling 解决的问题

Docling 是一条文档处理流水线，而不是单独的识字工具。它可以组合执行：

1. 读取 PDF 自带文字或页面图像；
2. 必要时调用 OCR 引擎识字；
3. 识别标题、正文、列表、图片和表格；
4. 推断阅读顺序和章节层级；
5. 识别表格行列关系；
6. 组装成带页码和出处的统一文档结构；
7. 导出 Markdown、JSON 等便于继续处理的格式。

Docling 可以选择 Tesseract、EasyOCR、RapidOCR 等不同 OCR 引擎。因此二者关系是：

```text
Docling 文档处理流水线
├─ PDF 读取
├─ OCR（需要时调用）
├─ 版面识别
├─ 表格结构识别
├─ 阅读顺序与章节组织
└─ 统一文档输出
```

### 1.3 三种实际情况

#### 情况 A：正常文字型 PDF

鼠标可以选中文字，复制后内容正常。

处理：优先 PDF.js，不需要 OCR。  
原因：直接读取原始文字通常更快，也避免 OCR 把正确字符识别错。

#### 情况 B：扫描版 PDF

整页是一张图片，无法选中文字。

处理：Docling 调用 OCR，再做版面和表格整理。  
原因：不经过 OCR 根本没有可搜索文字。

#### 情况 C：有文字但版面复杂

文字可以复制，但双栏顺序混乱、表格散开或警告框关系丢失。

处理：使用 Docling 的版面和表格能力；不一定需要重新做全页 OCR。  
原因：问题是结构错误，不是看不见字。

### 1.4 本项目分别检查什么

OCR 质量检查：

- ATV320、OHF 等关键字符串是否正确；
- 是否漏字或出现大量乱码；
- 中英文和数字是否混淆。

文档结构检查：

- 标题是否对应正确正文；
- 故障码、原因、警告和操作是否保持关联；
- 表格列有没有错位；
- 引用是否能回到正确页码；
- 阅读顺序是否正确。

所以“OCR 成功”不等于“文档可以入库”。两类检查都通过后才发布正式资料版本。

## 2. 方案四到底是什么

方案四由四个合作但权限不同的部分组成。

### 2.1 协调助手：像接待工程师

协调助手负责：

- 理解现场人员的自然语言；
- 把零散描述整理为现象、故障码、已做动作和未知信息；
- 在当前状态允许的工具中选择下一项；
- 阅读检索证据并草拟低风险方案；
- 证据不足时说明缺什么；
- 发现额外风险时请求提高风险等级或转人工。

它不负责：

- 判断用户最终是否有权限；
- 自己修改工单状态；
- 自己宣布设备恢复；
- 自己降低固定规则已经识别出的风险；
- 自己决定可以生成第三版方案。

### 2.2 状态机：像设备的安全联锁

状态机是一张由程序执行的状态转换表。它不理解长篇自然语言，只检查明确条件。

示例：

| 当前状态 | 收到的事件 | 必须满足的条件 | 下一状态 |
|---|---|---|---|
| 草稿 | 提交现场现象 | 用户、厂区和设备有效 | 排查中 |
| 排查中 | 证据不足 | 已保存检索记录 | 等待人工或补充信息 |
| 排查中 | 请求保存方案 | 证据充分、低风险、版本少于 2 | 等待用户确认 |
| 排查中 | 命中高危规则 | 无法由 AI 放宽 | 等待人工 |
| 等待用户确认 | 用户确认恢复 | 确认者和时间已记录 | 已解决 |
| 等待用户确认 | 第一版未恢复 | 有新的现场证据 | 排查中 |
| 等待用户确认 | 第二版未恢复 | 无需 AI 再判断 | 等待人工 |

如果协调助手在错误状态请求错误动作，状态机返回拒绝，而不是照做。

### 2.3 窄权限工具：像只能完成一种工作的按钮

协调助手不连接通用数据库控制台，只能调用明确工具：

| 工具 | 能做什么 | 不能做什么 |
|---|---|---|
| 读取工单上下文 | 读取当前允许看到的信息 | 读取其他厂区数据 |
| 检索官方资料 | 在当前设备允许的资料内搜索 | 搜索错误型号或未发布资料 |
| 追加现场观察 | 新增一条记录 | 覆盖或删除旧记录 |
| 执行风险判断 | 运行固定规则并记录结果 | 随意降低风险 |
| 保存方案草稿 | 保存带引用的草稿 | 直接标记方案成功 |
| 请求用户确认 | 请求状态机进入等待确认 | 替用户确认恢复 |
| 请求人工接管 | 创建接管请求 | 冒充工程师完成处理 |

“窄”不是功能弱，而是一次只给完成当前动作所必需的权限。

### 2.4 数据库：像工单账本和黑匣子

数据库分别保存：

- 用户原始描述；
- AI 整理后的结构化内容；
- 每次资料检索及候选结果；
- 最终采用的证据与页码；
- 风险规则命中情况；
- AI 生成内容及模型版本；
- 状态变化前后值和原因；
- 用户或工程师的实际确认。

历史采用追加记录，不能因为 AI 后来改变判断就覆盖旧结果。

## 3. 一条消息进入系统后发生什么

以“OHF，外壳温度较高，冷却风扇不转，还没有拆检”为流程示例。这里仅说明软件流转，不把示例当作真实维修指导。

1. 程序验证用户、厂区和设备权限。
2. 如果厂区和设备已确认，创建草稿工单并保存原始描述。
3. 协调助手调用“追加现场观察”，把现象和未做事项分开记录。
4. 状态机把工单从草稿推进到排查中。
5. 固定风险规则先检查是否存在必须直接转人工的内容。
6. 未被阻断时，协调助手调用资料检索工具。
7. 检索工具只在该设备标准型号和有效官方手册中搜索，保存关键词榜单、向量榜单、融合榜单和页码。
8. 程序检查证据是否属于正确型号、是否有出处、是否包含必要警告。
9. 证据不足则不生成确定性方案，进入补充信息或人工流程。
10. 证据充分时，协调助手生成结构化方案草稿，包括判断依据、步骤、停止条件、风险提示、引用和未知事项。
11. 程序再次检查方案中的动作是否命中危险规则、引用是否存在、方案版本是否超限。
12. 检查通过后保存方案，状态机进入等待用户确认。
13. 现场用户只反馈实际结果，不需要替 AI 证明原因。
14. 确认恢复后由程序记录确认人和时间，进入已解决；第一版未恢复且有新证据时回到排查中；第二版未恢复则转人工。

## 4. 为什么要先后检查两次风险

第一次检查用户输入，防止明显高危问题继续进入自动方案生成。

第二次检查 AI 生成的方案，防止用户描述本身不高危，但 AI 草拟的动作包含高危操作。

```text
用户输入 → 前置风险检查 → 检索与生成 → 方案风险检查 → 等待确认
              │                              │
              └────命中即转人工───────────────┘
```

固定规则和 AI 的关系是单向的：

- 固定规则说高危：必须高危。
- AI 发现新风险：可以提高为高危。
- AI 认为没事：不能推翻固定规则。

## 5. 结构化方案不是一段随意文字

协调助手必须返回固定字段，例如：

```json
{
  "summary": "对当前现象的归纳",
  "evidenceIds": ["资料段编号"],
  "assumptions": ["尚未确认的条件"],
  "steps": ["有序的低风险检查步骤"],
  "stopConditions": ["出现何种情况立即停止并转人工"],
  "expectedObservations": ["执行后需要记录什么"],
  "requestedTransition": "awaiting_user_confirmation"
}
```

程序逐项验证：没有证据编号、包含不允许动作、状态不合法或已经有两版方案，都会拒绝保存。

## 6. 这套设计的代价

- 比让 AI 直接写数据库多一层工具和状态代码；
- 每个状态转换都要编写测试；
- 新增业务流程时要修改状态表和权限表；
- 最终方案质量仍依赖生成模型和官方资料质量。

换来的能力是：安全规则不会只存在提示词里，AI 错误不会直接变成已解决工单，而且每一步可以复现和审查。这正是工业维修场景值得承担的复杂度。

## 7. E5 在这套系统中的位置

```text
现场描述 ──► E5 ──► 查询向量
资料段落 ──► E5 ──► 资料向量
                       │
                       ▼
                 比较语义是否接近
```

E5 不负责：

- 判断最终风险；
- 选择工单状态；
- 生成完整维修方案；
- 确认设备是否恢复。

因此以后还要选择一个生成模型作为协调助手的大脑。两类模型通过接口分开，未来更换任何一类都不需要重写整个工单流程。
