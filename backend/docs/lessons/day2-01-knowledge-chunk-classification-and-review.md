# 第二天第一节：先规定什么知识可以被助手使用

## 这一节做出了什么

我们还没有急着把 440 页手册全部切段，也没有生成向量。先给“知识片段”增加了一套进入检索系统前的质量门：

```text
机器提取或切分的原文
        ↓
模型提出三维候选分类
        ↓
人对照官方 PDF 核对正文和分类
        ↓
通过：可按规定用途进入后续检索
驳回：保留原因，但不能成为可用知识
```

三维分别是“内容是什么、原文危险等级、系统允许用途”。它们不能再被一个含义模糊的“风险标签”替代。

## 为什么先做规则，不先做向量

向量只能帮助找到意思相近的内容，不能证明内容正确、安全或适用于当前场景。如果先把提取错误和高危步骤全部变成向量，检索越快，错误传播也越快。

本节先决定“什么有资格被检索”，下一节再决定“怎样找到它”。这就是质量门在检索之前的原因。

## 一条真实数据怎样推动设计

NVE41300 第 50 个 PDF 页面包含 OHF 热阈值。页面视觉内容是 `118%`，基础文字提取中出现了 `1 18%`。这说明：

1. 官方文件是真实的，不代表自动提取一定正确；
2. 原始提取必须保存，方便定位工具错误；
3. 供检索使用的正文必须经过核对；
4. 审核必须留下人、时间和理由，不能只把状态改成“通过”。

所以数据库不是先凭想象画好，再拿数据往里塞；它被真实资料暴露的问题反向修改。

## 我们怎样让 AI 参与，而不是替人决定

模型可以一次准备完整候选：内容种类、资料危险等级、系统用途、核对正文建议和分类理由。审核人不需要从空白表格开始，只需对照官方页修改或确认。

但当前数据库规定：

- 新片段默认为待分类、待审核、仅供查阅；
- 模型不能仅修改审核状态就放行；
- 通过必须绑定一个真实系统用户，并记录核对正文、时间和理由；
- 驳回也必须说明理由；
- “小心、警告、危险”不得标为低风险现场指导。

这实现的是“模型做完整准备，人做最终确认”。

## 测试先行的全过程

每条规则都先写成一个会失败的反例：

1. 新测试读取 `content_kind`，旧表报字段不存在；
2. 加四个保守默认字段，测试通过；
3. 插入随意分类名，数据库错误地接受；
4. 增加固定允许值检查，随意分类被拒绝；
5. 构造“危险 + 低风险指导”，旧结构错误地接受；
6. 增加跨字段检查，矛盾组合被拒绝；
7. 只把状态改成“已通过”，旧结构错误地接受；
8. 增加审核人、时间、核对正文、理由和状态组合检查；
9. 用真实 `1 18%`/`118%` 例子证明原文和核对正文可以同时保留；
10. 用升级测试证明旧风险标签改名后数据仍在，没有因结构改造而丢失。

对应自动化规则为 R67—R77。本节完成时全项目运行70项测试并全部通过；项目当前为105项通过。

## 这节需要记住的五句话

1. 内容种类、来源危险等级、系统用途是三个不同问题。
2. 向量解决“找得像不像”，不解决“内容对不对、能不能用”。
3. 模型可以提出候选，但放行必须有可追踪的人类审核证据。
4. 机器原文和人工核对正文都要保存，不能用正确结果覆盖错误证据。
5. 数据库约束保护所有写入入口，提示词只约束某一次模型调用。

## 真实公司做法怎样帮助我们判断

IBM watsonx Orchestrate 的文档提取流程允许按提取可信度或空值触发用户复核，用户对照源文档修改后流程才继续；Microsoft Document Intelligence 的责任说明要求用真实业务样本评估提取质量，并在高风险场景保留人工监督。我们借鉴的是“自动准备 + 人工复核 + 留痕”的结构，而不是照搬它们的产品或阈值。

## 现在能做和不能做的事

已经能做：安全保存候选分类，拒绝非法值和矛盾组合，记录通过或驳回审核，并保留原文与核对正文。

还不能做：证明片段具体来自哪一个页面提取版本、把真实 OHF 内容正式切成片段、生成向量、评价检索质量、让助手生成维修方案。

下一节要补的是“片段来源链”：每个片段必须回指具体页面和具体提取结果，而不只是写一个页码。
