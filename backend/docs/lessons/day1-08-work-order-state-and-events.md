# 第一天第 8 课：工单状态、事件账本与短事务

## 1. 本批建出了什么

本批新增或改造：

- 改造 `work_orders`：增加创建成员、合法状态、解决时间和关闭时间约束；
- 新增 `work_order_events`：保存不可覆盖的全过程事件；
- 新增草稿工单创建服务：工单和第一条事件同一事务；
- 新增状态转换服务：只允许明确路径，并把状态变化和事件写入同一事务。

关键文件：

- `database/migrations/008_work_order_identity_status_and_events.sql`
- `src/work-orders/create-draft-work-order.ts`
- `src/work-orders/transition-work-order.ts`

## 2. 当前快照和历史账本为什么都要有

### `work_orders`：当前快照

回答：

- 工单现在是什么状态？
- 属于哪个厂区和设备？
- 当前列表中有哪些待人工工单？

如果每次看工单列表都重新计算全部历史事件，查询会复杂且缓慢，所以保留当前状态。

### `work_order_events`：历史账本

回答：

- 谁在什么时间提交了什么信息？
- 工单从哪个状态变到哪个状态？
- 为什么进入等待人工？
- 某次网络重试有没有写入两遍？

事件只允许新增。发现旧事件错误时新增一条更正事件，不能覆盖原记录。

## 3. 为什么创建人保存成员编号

只保存用户编号只能证明“这个人是谁”，不能证明“这个人在该厂区是否有角色”。

本项目保存：

```text
created_by_membership_id
```

并使用下面的联合关系：

```text
工单创建成员编号 + 工单厂区编号
              ↓
厂区成员编号 + 成员所属厂区编号
```

因此其他厂区的成员编号无法成为本厂区工单的创建人。

创建服务还会同时检查：

- 成员关系是否启用；
- 对应用户账号是否启用。

外键适合保证稳定关系，“当前是否启用”属于会变化的跨行条件，由事务服务检查。

## 4. 参与者类型和业务角色不能混为一谈

事件参与者类型只有：

- `user`：真实人员；
- `agent`：协调 Agent；
- `system`：确定性程序规则。

工程师不是第四种参与者类型。工程师仍然是 `user`，其成员记录中的角色是 `engineer`。

这样可以分别回答：

- 这条记录是人、Agent还是程序产生的？
- 如果是人，他当时在该厂区具有什么角色？

## 5. 为什么需要幂等键

现场网络可能超时，客户端会重复提交同一个请求。如果没有幂等键，两次提交可能产生两条相同事件。

本项目要求：

```text
同一工单 + 同一幂等键 = 最多一条事件
```

不同工单可以使用相同键，因为它们互不冲突。

## 6. 为什么事件禁止更新和删除

`work_order_events` 使用数据库触发器阻断更新和删除。

如果允许直接修改：

- AI可以把之前的错误判断悄悄覆盖；
- 用户反馈失败可能被后来的成功结果替换；
- 无法证明工单当时为什么转人工；
- 审查者看到的不是当时事实，而是后来整理过的故事。

正确做法是追加：

```text
原事件：风扇不转
更正事件：现场复核后发现风扇间歇转动
```

## 7. 草稿创建为什么必须使用一个事务

创建服务执行：

```text
检查活动用户和厂区成员
→ 插入草稿工单
→ 插入 work_order_created 事件
→ 一起提交
```

只要第二次插入失败，第一次插入也撤销。

事务内没有：

- 调用生成模型；
- 下载手册；
- 运行OCR；
- 等待人工输入。

这些慢操作放在事务外，避免长时间占用数据库锁。

## 8. 状态机第一批开放了哪些路径

```text
draft
├─ investigating
└─ cancelled

investigating
├─ awaiting_information
├─ awaiting_human
└─ cancelled

awaiting_information
├─ investigating
├─ awaiting_human
└─ cancelled

awaiting_user_confirmation
├─ investigating
└─ awaiting_human

awaiting_human
├─ human_processing
└─ cancelled
```

当前故意没有开放：

- `investigating → awaiting_user_confirmation`：要等有证据方案和风险判断表；
- `awaiting_user_confirmation → resolved`：要等现场确认表；
- `human_processing → resolved`：要等工程师处理记录；
- `resolved → closed`：要等关闭完整性检查。

这体现一个原则：状态名称可以先存在，但没有支撑记录之前，转换服务不能假装条件已经满足。

## 9. 状态转换为什么也要使用事务

状态转换服务执行：

1. 锁定一张目标工单；
2. 检查当前状态和目标状态是否允许；
3. 检查操作成员和用户是否仍启用；
4. 条件更新当前状态；
5. 追加 `status_changed` 事件；
6. 一起提交。

测试故意复用已存在的幂等键，让第5步违反唯一约束。验证结果是第4步也被撤销，工单仍保持原状态。

## 10. 数据库和状态服务分别保证什么

数据库保证：

- 状态文字来自允许集合；
- 创建成员与工单厂区一致；
- 事件与工单厂区一致；
- 用户事件具有成员身份；
- 幂等键不重复；
- 历史事件不能修改或删除；
- 解决和关闭时间与状态基本一致。

状态服务保证：

- 当前状态到目标状态的路径合法；
- 用户和成员当前仍启用；
- 更新快照和追加事件是一个事务；
- 当前尚无支撑记录的高级状态不能进入。

## 11. 迁移限制

规范型号可以从旧文字推断，因此上一批能自动回填。

旧工单的真实创建人却不能可靠推断。本项目目前是新建数据库，因此迁移直接要求 `created_by_membership_id` 非空。如果未来给已有生产库升级，必须先由业务方提供旧工单与真实创建成员的映射，不能编造一个创建人完成迁移。
