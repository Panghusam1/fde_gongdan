# 第三天教学01：怎样验证协调助手真的会办事

## 今天做出的东西

不是又写了一组普通单元测试，而是做出一套真实模型的“办事过程考试”：

- 20个模拟工单案例；
- 每个案例2轮，共40轮真实千问调用；
- 每轮都给模型当前数据库上下文和程序许可的动作；
- 检查动作、参数、禁止内容和整条过程是否通过；
- 保存数据版本、模型名、提示版本、耗时和逐轮原始决定。

原始题库在`data/evaluation/qwen-agent-trajectories-v1.json`，执行器在`src/evaluation/agent-trajectory-evaluation.ts`，原始结果在`reports/qwen-agent-trajectory-evaluation-v1.json`。

## 先理解三个层次

```text
第一层：输出是不是合法JSON
第二层：动作和参数是不是符合当前业务阶段
第三层：工具执行后，数据库最终状态是不是真的正确
```

本次真实模型评测重点覆盖前两层。第二天的确定性端到端测试覆盖第三层，但使用的是预设模型。下一步要把两者合并：真实模型实际调用工具，并检查数据库终态。

## 为什么每轮重新给数据库上下文

聊天记录只说明“说过什么”，数据库才说明“真正发生过什么”。例如模型说已经有方案，不代表方案表里真的存在方案；用户说自己是管理员，也不会改变厂区成员权限。

所以每一轮以数据库式上下文为准，模型只负责从当前许可动作中选一个。这个原则可以概括成：

> 模型负责理解文字，程序负责流程许可，数据库负责事实。

## 为什么要提前写合格线

如果先看成绩再定合格线，评测就变成解释成绩。提前冻结门槛后，模型、提示词和题库才能形成可比较基线。题库原文再用SHA-256指纹绑定，防止悄悄修改旧试卷。

本次门槛与结果：

| 指标 | 门槛 | 结果 | 怎么理解 |
|---|---:|---:|---|
| 合法结构输出率 | 100% | 100% | 40轮都能被程序解析 |
| 动作正确率 | 90% | 92.5% | 37/40选中单一预期动作 |
| 参数正确率 | 85% | 92.5% | 37/40动作及参数都符合检查 |
| 整条过程通过率 | 80% | 85% | 17/20案例的两轮全部通过 |

## 三个失败教会我们的事

三个案例中，程序同时允许“记录现场信息”和“检索官方资料”，题库只把检索当成正确答案。模型选择先记录用户的拆机请求或越权指令。

这说明评测失败有三种可能：

1. 模型真的选错；
2. 业务规则没有规定动作优先级；
3. 评分器把另一个合理动作误判为错。

必须阅读原始过程才能区分，不能只盯总分。本次同时发现协调循环会重复使用同一用户消息；失败测试真实重现了连续记录8次后达到最大步数。R188随后把规则放进程序：本轮记录一次后移除后续追加许可，再继续检索。因此真正修的是编排状态，而不是把提示词写得更凶。

## 这次结果能证明什么

- 真实千问在当前固定题库中全部返回合法结构；
- 对编号、第二版方案、高危、证据不足和型号边界等大多数固定上下文能选对动作；
- 当前提示和模型组合达到了事先门槛；
- 已经有可复跑的回归基线。

## 不能证明什么

- 这些案例是项目模拟数据，不是20张真实厂区工单；
- 固定上下文重放不是模型亲自执行工具后的真实状态变化；
- 一次运行不能证明滚动模型版本长期稳定；
- 85%整条通过率不是生产上线标准；
- 工业方案内容尚未经过真实ATV320工程师批准。

## 需要记住的面试表达

不要说“我做了40轮，准确率92.5%，所以可上线”。准确说法是：

> 我先冻结20条、40轮协调决策基线，用真实模型验证结构、动作和参数；首轮达到100%、92.5%、92.5%和85%。逐条复盘发现三个失败来自许可动作歧义，并进一步定位到同一用户消息被重复记录的编排风险；我保留v1原始报告，用R188先复现连续记录到步数上限，再实现本轮输入单次消费，同时把真实数据库终态评测列入下一层，而没有通过降低门槛或改答案美化成绩。
