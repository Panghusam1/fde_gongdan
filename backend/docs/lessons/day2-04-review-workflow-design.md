# 第二天第四节：FDE 怎样设计并实现专业审核流程

## 先纠正学习边界

FDE 不需要判断“42V 是否危险”“某个复位操作是否适合现场执行”。这些是变频器领域工程师的专业职责。

FDE 要解决的问题是：当模型给出一个可能正确、也可能错误的完整建议时，系统怎样让专业人员快速确认，又怎样保证模型不能自己批准、修改不能丢失、正式知识都有证据。

本项目从此不再把设备专业判断题当作 FDE 练习题。手册内容只作为系统设计的真实数据样本。

## 当前系统已经有什么

当前候选知识已经有：

- 官方资料版本；
- PDF 页码和页内精确字符范围；
- 机器提取原文；
- 模型提出的内容种类、原文危险等级和系统用途；
- 待审核、已通过、已驳回三种状态；
- 审核人、审核时间、核对正文和审核理由字段；
- 已审核记录不可修改的数据库门禁。

但还缺一个关键答案：如果人工修改了模型建议，系统怎样同时保留“模型原来建议什么”和“人工最后确认什么”？只保留最后结果，不足以复盘模型错误，也无法形成可靠评测数据。

## 三种留痕方案

### 方案一：直接覆盖原记录

审核人修改候选行，然后把状态改成已通过。

优点：实现最简单，读取正式知识也方便。

缺点：模型原建议被覆盖，无法统计模型哪些字段经常判断错误，也无法向面试官解释人工到底改了什么。

结论：不采用。

### 方案二：候选表和正式知识表完全分开

候选永远不改；通过后复制一份到正式知识表。

优点：机器建议和人工结果边界最清楚。

缺点：来源关系、版本关系和分类字段需要复制或跨表关联；查询、唯一性和后续修订都更复杂。对于一周案例，成本过高。

结论：当前不采用。如果未来出现多人多轮审批、知识发布批次和回滚要求，再升级到该模型。

### 方案三：主表保存当前结果，审核事件表追加前后快照

审核服务在同一个事务里完成两件事：更新知识片段的最终状态，同时新增一条不可修改的审核事件。事件保存审核前快照、审核后快照、审核动作、审核人、时间和理由。

优点：正式检索仍只读一张主表；又能完整比较模型建议和人工结果。

缺点：主表与事件快照存在受控重复，必须用一个事务保证两者同时成功或同时失败。

结论：本项目选择方案三。重复不是随意复制，而是为了审计保存当时状态；主要业务字段仍使用关系字段，前后快照才使用 `jsonb`。当前一个候选只能有一次终态审核；需要重新提交时创建新候选，而不是覆盖旧记录。

## 一次审核应怎样运行

```text
领域工程师打开审核任务
  → 左侧查看官方PDF页面和高亮原文
  → 右侧查看模型的完整建议与理由
  → 点击确认，或修改后填写理由，或驳回
  → 服务验证人员权限和候选当前状态
  → 锁定候选，避免两个人同时批准
  → 服务更新主记录，数据库触发器在同一事务中自动写审核事件
  → 事务成功后，正式知识才可使用
```

“一键确认”不是没有审核，而是模型已经把字段填完整，专业人员只需对照证据确认。出现 `1 18%` 这类提取差异时，人工可以把核对正文改为 `118%`，审核事件同时保留修改前后值与理由。

## 五类职责不能混

| 参与者 | 负责什么 | 不能做什么 |
|---|---|---|
| 模型 | 提出完整候选、理由和来源 | 批准自己的候选 |
| 程序 | 检查权限、状态、来源和事务 | 判断设备工程含义 |
| 数据库 | 保证字段、关联、不可变和同时成功/失败 | 理解维修语义 |
| 领域工程师 | 确认设备含义和安全用途 | 绕过证据直接发布 |
| FDE | 设计数据、流程、权限、审计和测试 | 冒充变频器工程师 |

## 哪些规则放在哪里

### 放数据库

- 审核动作只能使用统一值；
- 审核人必须是真实用户；
- 审核事件必须关联真实候选；
- 已通过必须有核对正文、审核人、时间和理由；
- 审核后的知识和审核事件不能被静默修改；
- 外键列建立索引，便于按候选和审核人查询。

### 放服务代码

- 当前登录者是否具有该产品族的知识审核资格；
- 只能审核仍处于待审核状态的候选；
- 使用行锁避免两个审核请求互相覆盖；
- 更新主记录时由数据库在同一个事务中自动新增事件；
- 正式接入身份系统后，审核人编号必须来自可信登录会话，不能接受模型自由填写。

### 交给领域工程师

- 提取值是否忠实于视觉原文；
- 分类和用途是否符合设备含义、法规与厂区制度；
- 模型建议应确认、修改还是驳回。

## 为什么真实产品也这样做

IBM watsonx Orchestrate 的文档提取流程会在置信度不足或结果为空时创建用户审核任务；审核人可以对照文档修改提取值，提交后流程才继续。它的评测功能还要求人先核对正确值，再计算准确率。这证明“模型先填完整候选、人员核对、流程继续”是实际企业产品采用的工作方式。

Microsoft Document Intelligence 的透明度说明建议高风险使用保留人工监督，并说明人工环节可以处理文档识别未达到要求的情况。它证明高风险文档处理需要人工责任边界，但没有替我们规定具体表结构。

PostgreSQL 官方文档说明事务能把多个步骤组成同时成功或同时失败的操作；触发器能读取修改前后的行。这是“更新正式状态 + 保存审核事件”技术上可实现的依据，但设备审核政策仍是本项目的业务设计。

## 实际实现结果

- 迁移 `015_audit_knowledge_chunk_reviews.sql` 新增产品族审核资格和不可变审核事件；
- 审核事件不是由业务代码“记得去写”，而是由状态变更触发器自动生成；
- `review-knowledge-chunk.ts` 支持一键确认、修改后确认和说明理由后驳回；
- 服务使用行锁读取候选，检查用户与审核资格都处于启用状态，并严格匹配资料所属产品族；
- 11项专项测试覆盖授权、跨产品越权、前后快照、驳回、重复审核、缺修改理由和事务回滚。

## 这一节应该记住

1. FDE 不给设备知识判对错，而是设计谁有权判、依据是什么、结果怎样留下。
2. 一键确认的前提是模型提交完整建议，不是模型自动批准。
3. 只保存最终值无法审查 AI；必须保留建议值和确认值。
4. 本项目选择“主表当前结果 + 不可变审核事件”，兼顾查询简单和完整留痕。
5. 程序验证流程一致性，领域工程师确认专业正确性，两者不能互相代替。
6. 厂区工程师角色和产品知识审核资格不是一回事，权限范围必须按业务对象建模。
7. 能由数据库自动生成的审计记录，不应依赖每条业务代码自觉填写。
