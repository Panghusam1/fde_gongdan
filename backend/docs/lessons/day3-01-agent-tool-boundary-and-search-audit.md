# 第三天第一节：让协调助手通过窄工具检索，而不是直接操作数据库

## 这一节做出的东西

实现了`search_official_knowledge`窄工具。协调助手给出工单和问题，系统自动完成：

```text
验证当前登录成员
  → 从工单找厂区和设备
  → 从设备找规范型号和产品族
  → 只查当前有效资料中的已审核知识
  → 运行关键词与向量检索
  → 重新验证权限和设备范围
  → 保存检索、排名、引用和工单事件
  → 返回可核验证据
```

## 什么叫“窄工具”

窄工具不是功能少，而是只暴露完成一个业务目的所需的最小输入和能力。

如果给AI一个通用SQL工具，它既能查资料，也能读用户、改工单甚至删除数据。提示词里写“不要乱操作”不是安全控制。

本工具没有`productFamilyId`参数。产品族由工单设备自动推导，因为设备适用范围属于业务事实，不能让AI猜。

## AI、程序和数据库怎样分工

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 协调助手 | 理解用户问题，决定何时请求检索，阅读返回证据 | 决定自己有无权限、自由选择产品族、执行SQL |
| TypeScript服务 | 验证会话成员、推导设备范围、调用检索、处理幂等、组织事务 | 判断设备维修结论是否专业正确 |
| PostgreSQL | 保证工单/厂区/设备/型号/产品族关系一致，保存不可变审计 | 理解自然语言问题 |
| 领域工程师 | 审核知识和安全用途 | 绕过系统来源与审计 |

## 为什么权限检查不能只做一次

查询向量的模型计算在事务外进行。这样不会因为模型慢而长期锁住工单，但会出现时间差：第一次检查通过后，用户可能被停用，设备型号也可能被管理员修正。

所以结果写入前必须再检查一次。如果两次之间权限或设备范围发生变化，整次结果作废，不留下半条检索，也不返回给AI。

这叫“使用结果前重新确认前提”，比简单地把所有操作塞进长事务更适合外部模型调用。

## 为什么零结果也要保存

“没有找到当前有效证据”本身会影响后续流程：系统应该补充信息或转人工，而不是让AI凭常识编答案。

因此一次零结果检索仍保存：问题、工单、设备、产品族、模型版本和时间，并追加工单事件，只是命中记录为0条。

## 为什么引用不能只给页码

只有“第72页”无法确定是哪份文件、哪个版本。完整引用至少要包含资料编号、版本、文件摘要和页码；字符范围与逐字摘录进一步证明系统没有把相邻警告或步骤错误带入。

这与前面学过的原则一致：页面位置不能决定知识边界，业务目的和风险边界才能决定知识边界。页码是位置，逐字范围和业务片段共同确定证据。

## 为什么要记录三套名次

每条命中保存：

- 关键词原始名次和分数；
- 向量原始名次和相似度；
- 最终融合名次和分数。

只保存最终结果无法解释将来为什么调整门控。保存原始路线后，可以区分“向量模型找错”“关键词污染”“融合参数错误”和“源资料根本没有答案”。

## 幂等重试的内部逻辑

第一次请求成功后，同一网络请求可能因为客户端没收到响应而重发。

- 工单、幂等键、问题、模型和参数完全相同：返回原结果；
- 幂等键相同但问题或模型不同：拒绝；
- 不重新计算向量，不重复写事件。

幂等不是简单地“遇到重复就忽略”，而是先证明重复请求的业务内容一致。

## 本阶段遇到的三个真实调整

### 调整一：最初结果缺少可核验引用

第一版工具只返回知识正文、片段编号和排名。设计复查发现协调助手无法说明来自哪份手册、哪个版本和哪一页。

新增R141后，工具通过一次批量查询返回发布方、资料编号、官方网址、版本、文件摘要、页码、字符范围和逐字摘录。

### 调整二：只检查片段审核状态，遗漏资料版本状态

第一版检索会返回已审核片段，即使所属手册后来被撤回。新增R142后，两条检索SQL都要求资料版本为`current`。

这个变化让旧的R129—R131失败。排查发现不是新门禁错误，而是旧测试夹具从未把资料设为当前有效版。最终修正测试前提，没有删除生产门禁。

### 调整三：停用用户被误报为工单不存在

授权查询最初能阻止停用账号，但连接条件把该行完全过滤掉，错误信息变成“工单不存在”。新增R143精确复现后，把授权状态改成明确布尔值，统一返回授权错误，并证明模型调用次数为0。

## 为什么使用复合外键

单独验证每个编号存在仍可能拼出矛盾组合，例如工单是真实的、设备也是真实的，但二者不属于同一厂区。

复合外键直接表达“这几个编号必须在父表同一行中共同出现”。因此数据库能拒绝：

- 工单与设备不一致；
- 设备与规范型号不一致；
- 规范型号与产品族不一致；
- 请求成员与工单厂区不一致。

## 真实公司和产品为什么这样做

Amazon Bedrock AgentCore Gateway允许企业把现有API和Lambda定义为Agent工具，并配置进站、出站授权及凭据交换。它说明正式Agent平台并不是把后台系统全部交给模型，而是通过有结构、可授权的工具连接。

OWASP把过多功能、过大权限和过度自主列为Agent风险，明确建议下游系统完成授权、工具只保留最小功能，并在具体用户上下文中执行。

参考：

- [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)
- [AgentCore Gateway工作流](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-building.html)
- [OWASP LLM06:2025 Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- [PostgreSQL复合外键与约束](https://www.postgresql.org/docs/current/ddl-constraints.html)

它们证明设计模式真实存在，不证明本项目已经使用AWS，也不证明本项目字段是这些产品的内部实现。

## 这一节应该记住

1. Agent不应该拿到通用SQL，只拿完成业务目标所需的窄工具。
2. 厂区、设备、型号和产品族要从工单关系推导，不能让AI自由填写。
3. 登录身份必须由可信会话注入，不能从模型输出读取。
4. 模型调用前验权，结果写入前还要重新验权。
5. 外部模型放事务外，数据库写入保持短事务。
6. 没有成功留痕的检索结果不能交给AI使用。
7. 零结果是重要业务事实，也要记录。
8. 检索证据必须包含资料版本、文件摘要、页码和逐字范围。
9. 幂等重试必须核对请求内容一致，不能只按一个键盲目去重。
10. 片段通过审核仍不够，所属资料版本还必须当前有效。

## 下一步

把检索结果送入风险判断工具。程序先根据内容种类、原文危险等级和用途执行不可绕过的规则；只有低风险且证据完整时，协调助手才可以草拟第一版方案。
