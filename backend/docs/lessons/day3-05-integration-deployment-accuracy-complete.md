# 第三天完整教学：联调、部署与准确率优化

## 0. 今天到底要做出什么

第三天不是继续堆功能，而是把前两天做出的零件变成一个可以验证、可以交付、知道怎样上线的系统。

今天结束时应该有六个产物：

1. 一条唯一正式主链，不允许测试使用新版、正式入口仍使用旧版；
2. 一组端到端联调测试，能够检查工具轨迹和数据库最终状态；
3. 一套开发集、首次未见集、回归集分离的准确率优化方法；
4. 一份失败分类表，知道问题应改数据、检索、模型、规则还是编排；
5. 一份测试环境和生产环境部署方案，明确当前已经实现与尚未实现的部分；
6. 演示、评测报告、发布清单和面试问答。

本项目当前已经完成前四项和本地演示；测试环境服务化、正式 PostgreSQL、容器发布、线上监控和生产流量尚未实施。`npm run demo` 是可重复交付，不等于已经生产部署。

## 2. 先学会区分四个词

### 2.1 单元测试

只验证一个小部件。例如：语言代码能否统一为 `zh-CN`，重复候选编号能否被拒绝。

### 2.2 集成测试

验证两个以上真实部件能否按约定连接。例如：检索命中编号能否沿数据库外键查到资料编号、版本和语言。

### 2.3 端到端测试

从一张新工单开始，让请求经过检索、证据、风险、方案和确认，最后检查工单表、证据表、风险表、方案表和人工接管表的终态。

### 2.4 部署

把系统变成一个其他人或其他系统能够稳定访问的运行单元，并具备持久数据、配置、密钥、健康检查、日志、监控、备份和回滚。能在开发者电脑执行命令，只能算本地交付。

## 3. 本项目的真实联调链路

```text
用户确认厂区、设备和资料身份
  ↓
创建草稿工单并保存现场观察
  ↓
第四版正式主链读取数据库当前状态和允许动作
  ↓
协调模型只能从允许动作中选一个
  ↓
工单范围检索
  ├─ 产品族和厂区权限由程序先过滤
  ├─ E5 只在合法范围内召回候选
  └─ 保存检索批次和命中编号
  ↓
来源约束
  ├─ 数据库核对资料编号、版本、语言
  ├─ 无精确匹配：不调用内容模型，证据不足
  └─ 有精确匹配：只把匹配正文交给内容判断器
  ↓
风险门
  ├─ 固定高危规则
  ├─ 官方证据用途与警告
  └─ 模型只能提高风险，不能降低程序风险
  ↓
最多两版证据方案
  ↓
用户确认恢复，或高危/证据不足/两版失败转人工
  ↓
核对数据库终态和全过程审计
```

### 为什么正式主链必须只有一个组装入口

如果每个测试自己拼接模型、检索器和证据判断器，就可能出现“专项测试用了新版，正式业务仍在用旧版”。本项目真实出现过这个问题：第六版来源判断器专项测试通过，但三套端到端测试仍创建第五版。

解决方法不是在更多地方手动替换，而是建立唯一正式工厂：

- `createWorkOrderMainChainV4` 固定协调提示版本；
- 固定第八版内容判断器；
- 固定数据库来源绑定版本；
- 固定结构化来源约束版本；
- 启动时发现版本不符直接报错。

这一设计叫“组装点收口”：组件可以有多个历史版本，正式业务只有一个被批准入口。

## 4. 联调不是一起运行，而是逐层核对契约

“契约”就是上游必须提供什么、下游保证返回什么、失败怎样表示。

| 层 | 输入契约 | 输出契约 | 本项目的检查方法 |
|---|---|---|---|
| 配置层 | 模型地址、模型名、密钥、固定版本 | 可用且不泄露的运行配置 | 缺配置立即失败；密钥不写报告 |
| 数据库层 | 迁移文件、基础资料、审核状态 | 表、外键、唯一约束和事务可用 | 迁移测试、约束测试、全新数据库重放 |
| 检索层 | 工单、问题、产品范围、审核知识 | 检索批次和候选编号 | 首位、前三、错型号拒绝、无答案行为 |
| 来源层 | 候选编号和人工确认来源 | 精确匹配候选或程序拒绝 | 无匹配必须零内容模型调用 |
| 证据层 | 去掉来源指令后的内容问题和匹配正文 | 直接回答、部分相关、不能回答 | 引用必须是候选原文的连续片段 |
| 风险层 | 原始问题、证据用途、固定政策 | 风险级别、命中规则、是否允许方案 | 高危分支不能产生方案 |
| 协调层 | 数据库上下文和当前允许动作 | 单个合法动作与参数 | 结构、动作、参数、整条轨迹 |
| 终态层 | 工具真实执行结果 | 解决、等待人工或继续调查 | 直接查各业务表的记录数量和状态 |

### 联调时的正确运行顺序

```powershell
# 1. 先测新版组装入口和来源约束
node --test tests/work-order-main-chain-v4.test.ts tests/source-identity-unseen-executor-v4.test.ts

# 2. 再测窄工具和确定性完整流程
node --test tests/work-order-resolution-flow.test.ts tests/work-order-evidence-validation.test.ts

# 3. 再测稳定的离线双分支演示
npm.cmd run demo

# 4. 最后跑全量无费用回归
npm.cmd test

# 5. 真实模型能力门只按登记命令单独运行，不能混入默认测试
npm.cmd run report:model-tests
```

### 为什么必须从小到大

如果全量流程失败，你只知道“系统不对”；如果前七层都有独立证据，失败范围可以迅速缩小。例如：

- 没生成方案，先看风险表，而不是先怀疑协调模型；
- 检索结果为空，先看产品范围和审核状态，再看 E5；
- 来源不匹配，先看数据库资料版本，不让模型解释；
- 方案编号错误，先看数据库状态绑定，不继续加提示词。

## 5. 本项目联调中四个真正的问题

### 问题一：同一条用户消息被重复消费

现象：协调助手连续追加同一观察八次，直到达到最大步数。

定位：模型每轮都看到同一消息，程序又一直允许 `append_observation`。

根因：本轮输入有没有消费是编排状态，不是语言理解问题。

调整：一轮记录后，程序移除本轮后续追加许可，再继续检索。

记忆：模型可以选择动作，程序必须保证消息只能产生一次业务副作用。

### 问题二：模型填写数据库内部编号不稳定

现象：证据判断正确，但模型填写了错误的风险记录编号或方案编号，端到端首跑只有 5/12。

定位：单独的语义判断通过，数据库终态失败；错误集中在模型生成的内部主键。

根因：内部编号是数据库事实，却交给模型回忆和复制。

调整：程序用当前工单最新有效状态覆盖模型填写的内部编号。

记忆：自然语言由模型理解，数据库主键由程序绑定。

### 问题三：来源身份连续三批未见失败

现象：提示词要求不得伪造版本和语言，但新表达仍能让模型把第 05 版当作第 06 版，或把中文资料当英文资料。

定位：同一问题复跑仍会错误；继续补提示样例只能修已知表达。

根因：把编号、版本、语言这种确定性相等判断交给了生成模型。

调整：人工确认结构化来源，数据库先精确过滤；没有匹配时零模型调用拒绝。

结果：第四批首次未见 11/12，五条无匹配来源 5/5 程序拒绝，错误来源接收 0。

记忆：准确率优化的最高收益，常常不是换更大模型，而是把不该由模型做的事拿回来。

### 问题四：新主链破坏旧首跑证据

现象：新业务回归 12/12，但全量测试三项失败，因为旧执行器文件摘要变化。

根因：为了接新主链直接修改了历史首次运行封存文件。

错误做法：把旧摘要更新成新值，这相当于考试后改试卷封条。

调整：恢复旧执行器，新增版本化执行器和新封存记录。

记忆：业务结果正确不等于发布验收通过；历史可复现性也是发布门。

## 6. 准确率到底怎样拆

不能只说一个“系统准确率”。本项目至少有五层指标：

| 层 | 指标 | 回答的问题 |
|---|---|---|
| 召回 | 首位命中、前三命中 | 正确证据有没有被找进来 |
| 证据 | 直接回答、部分相关、不能回答、引用正确 | 候选是否真的回答问题 |
| 安全 | 高危漏拦、正常误拦、危险误方案 | 系统是否在不该自动化时停下 |
| 协调 | 结构、动作、参数、完整轨迹 | 模型是否会按当前状态办事 |
| 业务 | 工单最终状态、接管理由、各表记录 | 整个系统是否做成正确结果 |

### 本项目的指标不能混在一起

- E5 首位 76.7% 不等于工单正确率 76.7%；
- E5 前三 100% 只说明候选召回，不说明前三都能当证据；
- 12 条端到端 11/12 不等于生产准确率，因为题目是项目自建；
- 高危 5/5 是硬安全分支结果，不能被总体平均数稀释；
- 演示 2/2 是流程稳定性，不是模型能力成绩。

## 7. 准确率优化的标准循环

### 第一步：冻结现状

记录：代码摘要、数据集摘要、模型名和版本、提示版本、检索参数、预期门槛。先写门槛，再运行。

### 第二步：使用真正没见过的数据

开发集允许反复查看和调试；首次未见集在首跑前封存；首跑一旦看过就变成回归集，不能继续称为未见数据。

### 第三步：逐条归类失败

| 失败类型 | 典型表现 | 应改的层 |
|---|---|---|
| 数据问题 | 标准答案本身歧义、资料缺失 | 数据和人工审定 |
| 范围问题 | 错型号、错厂区、错版本仍进入检索 | 数据库过滤和权限 |
| 召回问题 | 正确片段未进前三 | 切片、嵌入模型、查询改写、索引 |
| 精排问题 | 正确片段进前三但不是第一 | 二次排序或证据判断 |
| 拒答问题 | 资料没有答案仍强行选一段 | 独立证据存在性判断 |
| 安全问题 | 关闭保护请求得到方案 | 固定风险门和人工接管 |
| 编排问题 | 重复写入、错误编号、第三版方案 | 状态机、事务和工具许可 |
| 模型接口问题 | 无效 JSON、超时、401 | 结构校验、重试、权限和配置 |

### 第四步：选择最小但正确的调整

优先级通常是：

1. 修错误标签和缺失资料；
2. 用数据库确定范围、权限、版本和状态；
3. 改切片和检索；
4. 增加独立证据判断或二次排序；
5. 调整提示；
6. 最后才考虑更换更大模型。

提示词成本低，但它不能替代权限、事务、唯一约束和精确相等判断。

### 第五步：三种测试一起过

1. 已知失败回归：证明缺陷被修；
2. 新首次未见：证明不是只记住旧题；
3. 全量回归：证明没有破坏其他能力和历史证据。

### 第六步：只发布达到预先门槛的版本

如果总体 11/12，但出现一条错误来源放行，仍要按安全硬门判失败。工业系统不能用普通题的高分抵消高危错误。

## 8. 本项目的准确率优化路线

```text
10题小样本：E5首位90%
  ↓ 扩到40题
E5首位76.7%，前三100%；混合首位73.3%
  ↓
结论：保留E5做候选召回，不宣称混合更好
  ↓ 尝试0.86相似度拒答
新24题无答案拒答83.3%，失败
  ↓
结论：相似度不是“资料有答案”的概率
  ↓ 增加独立证据判断
第三批18题首次未见：17/18，通过冻结门槛
  ↓ 接入完整工单
首次端到端5/12：模型编号不稳定 + 问题超出原文
  ↓ 程序绑定数据库状态 + 修正数据标准
新12条端到端11/12，安全5/5
  ↓ 增加来源身份
三批来源未见持续暴露提示词覆盖
  ↓ 结构化确认 + 数据库精确过滤
第四批来源首次未见11/12，无匹配5/5，错误来源接收0
```

这条路线说明：准确率优化不是一条分数不断上升的直线，而是每次扩展数据后发现旧指标没有覆盖的新错误，再调整职责边界。

## 9. 为什么选这些技术

### TypeScript

用途：给工具入参、模型决定和业务状态建立静态结构；测试与业务代码使用同一种语言，减少接口翻译。

适合本项目：团队要快速做出可测试原型，业务对象和工具参数多，类型能够在运行前暴露一部分拼装错误。

边界：类型只在编译和开发阶段帮助检查，外部模型返回仍必须在运行时校验。

### PGlite

用途：测试时在进程内启动真正的 PostgreSQL 内核兼容环境，每个案例使用全新数据库。

适合本项目：无需安装数据库服务，能够高速重放迁移、约束和事务。PGlite 官方说明默认内存文件系统不会持久保存，Node 文件系统模式才能落盘，因此本项目只把内存模式用于测试和演示，不当作多人生产数据库。[PGlite 文件系统官方说明](https://pglite.dev/docs/filesystems)

### PostgreSQL 与 pgvector

用途：工单、权限、版本等关系数据和知识向量放在同一事务数据库中。

适合本项目：来源身份需要沿外键精确追溯，向量只负责同一合法范围内的相似检索，放在同库可以减少两套数据之间的同步问题。pgvector 官方说明小数据可以做精确近邻搜索，HNSW 和 IVFFlat 是以召回换速度的近似索引；当前候选很少，不应为了“先进”提前上近似索引。[pgvector 官方说明](https://github.com/pgvector/pgvector)

成熟案例：SurveySparrow 将独立向量库迁到 Aurora PostgreSQL + pgvector，把关系数据和向量合并；施耐德电气也公开使用 Aurora、pgvector 和生成模型处理客户层级业务。案例证明这种组合用于企业业务是成熟路径，但不证明本项目已经具备同样规模。[SurveySparrow 案例](https://aws.amazon.com/blogs/database/accelerating-developer-productivity-in-the-agentic-ai-era-with-amazon-aurora-postgresql/)、[施耐德电气案例](https://aws.amazon.com/blogs/database/schneider-electric-automates-salesforce-account-hierarchy-management-with-generative-artificial-intelligence-ai-using-amazon-aurora-and-amazon-bedrock/)

### multilingual-e5-small

用途：把中文口语问题与中文手册片段映射成可比较向量，作为第一阶段候选召回。

适合本项目：模型较小、可以本地运行、中文与多语言资料可共用一套接口。E5 研究论文将它定位为通用单向量文本表示，可用于检索、聚类和分类；项目仍用自己的40题证明实际效果，而不是引用公开榜单代替验收。[E5 原始论文](https://arxiv.org/abs/2212.03533)、[多语言 E5 技术报告](https://arxiv.org/abs/2402.05672)

### 千问协调模型与内容判断模型

用途：协调模型选择当前允许动作；内容模型判断匹配正文能否回答问题。

适合本项目：已有百炼环境，中文能力和结构化输出满足项目原型。千问官方说明函数调用由模型返回工具名和参数、应用程序实际执行工具；结构化输出在交给下游前仍必须校验，这与“模型选择、程序执行”的边界一致。[千问工具调用官方说明](https://help.aliyun.com/zh/model-studio/qwen-function-calling)、[结构化输出官方说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

### 单协调助手加程序状态机

用途：一个模型理解本轮意图，程序根据数据库状态只开放当前合法工具。

为什么没有使用多智能体或图编排框架：本项目只有一个工单业务单元，动作顺序和风险边界明确；增加多个自主角色会增加状态同步、权限和调试成本。LangChain 公开的 Klarna、PagerDuty、Modern Treasury 等案例说明图式编排适合更复杂的生产智能体，但不能据此强行套到本项目。[LangChain 客户案例](https://www.langchain.com/customers)

### 结构化元数据过滤

用途：先按资料编号、版本、语言筛选，再进行语义判断。

成熟案例：Ring 的全球客服问答系统公开使用元数据驱动的地区内容过滤，并把资料摄取、评测和发布分开。它与本项目的“结构化来源过滤 + 评测后晋级”高度相似；差别是 Ring 已在多地区生产运行，本项目仍是本地原型。[Ring 官方联合案例](https://aws.amazon.com/blogs/machine-learning/how-ring-scales-global-customer-support-with-amazon-bedrock-knowledge-bases/)

## 10. 部署要分三级

| 能力 | 本地演示 | 测试环境 | 生产环境 |
|---|---|---|---|
| 调用入口 | 命令行 | 内部网络接口 | 有鉴权、限流的正式接口 |
| 数据库 | 内存 PGlite | 独立 PostgreSQL + pgvector | 高可用 PostgreSQL、备份、恢复演练 |
| 数据 | 固定种子 | 脱敏测试资料 | 审核通过的真实资料和版本发布 |
| 模型 | 可控模型或显式真实模型 | 测试业务空间与限额 | 独立生产业务空间、配额和故障降级 |
| 密钥 | 本机环境文件 | 测试密钥管理 | 生产密钥管理、最小权限、轮换 |
| 监控 | 控制台输出和测试报告 | 请求追踪、日志、基础指标 | 告警、值班、审计、成本和质量漂移 |
| 发布 | 手动命令 | 自动构建和部署 | 小流量发布、能力门、回滚 |
| 当前状态 | 已完成 | 未实施 | 未实施 |

### 为什么当前不能叫“部署完成”

项目还没有网络服务入口、持久 PostgreSQL、容器镜像、健康检查、线上请求追踪和真实回滚演练。把 `npm run demo` 放进简历时应写“封装可重复演示”，不能写“完成生产部署”。

### 测试环境应怎样搭

```text
内部测试用户
  ↓ HTTPS + 身份认证
工单服务（Node/TypeScript）
  ├─ 第四版正式主链
  ├─ 请求编号和工单编号贯穿日志
  └─ 模型调用超时、重试、限额和降级
  ↓
测试 PostgreSQL + pgvector
  ├─ 业务关系表
  ├─ 审核知识和向量
  └─ 迁移记录、备份和恢复验证
  ↓
百炼测试业务空间

旁路：日志、指标、调用追踪、错误告警
```

### 生产发布的正确顺序

1. 构建固定依赖版本的制品；
2. 在空数据库执行迁移并在旧版本数据副本上演练升级；
3. 导入通过审核的资料，生成并校验文件摘要和向量版本；
4. 配置独立生产密钥、最小权限和调用限额；
5. 运行数据库、模型、检索和人工接管的就绪检查；
6. 跑稳定冒烟测试与安全能力门；
7. 先影子流量或内部试用，再小流量放开；
8. 监控错误、耗时、转人工率、危险误方案和模型费用；
9. 任何硬门失败立即回滚代码、提示、模型或知识版本；
10. 上线后把脱敏真实失败加入新的评测集。

详细操作见 `docs/deployment/test-and-production-deployment-runbook.md`。

## 11. 上线前看哪些指标

### 系统指标

- 请求成功率；
- P50、P95 和 P99 总耗时；
- 数据库连接数、慢查询、锁等待；
- 模型超时、限流、重试与费用；
- 检索耗时和候选数量；
- 人工接管队列长度和等待时间。

PostgreSQL 官方提供 `pg_stat_activity`、数据库和索引统计、锁与备份进度等视图用于运行监控。[PostgreSQL 监控官方文档](https://www.postgresql.org/docs/current/monitoring.html)

### 业务质量指标

- 来源不匹配程序拒绝率；
- 错误来源接收数，目标必须为 0；
- 高危漏拦数，目标必须为 0；
- 正常问题误转人工率；
- 证据不足正确接管率；
- 第一版解决率、第二版解决率、两版失败率；
- 人工改写方案比例；
- 工单最终闭环率。

### 每次请求必须留下什么

- 请求编号、工单编号和检索批次编号；
- 代码版本、数据版本、模型版本和提示版本；
- 确认的资料编号、版本和语言；
- 当时允许的动作、模型选择和工具真实结果；
- 命中的政策编号、证据编号和最终状态；
- 每一段耗时、模型用量和错误类型。

OpenTelemetry 把一次请求拆成可关联的追踪、指标和日志，是适合测试与生产联调的行业通用方法；阿里云百炼的应用观测也能查看向量生成、检索和模型调用链，并把线上调用加入评测集。[OpenTelemetry 官方说明](https://opentelemetry.io/docs/)、[百炼应用观测官方说明](https://help.aliyun.com/zh/model-studio/application-observation)

## 12. 发布硬门与回滚

### 发布硬门

以下任一项失败都不能发布：

- 数据库迁移或回滚演练失败；
- 默认全量回归出现失败；
- 新首次未见数据未达到预先门槛；
- 高危漏拦大于 0；
- 错误来源接收大于 0；
- 高危或证据不足分支生成了方案；
- 人工接管入口不可用；
- 模型密钥、权限或费用上限未配置；
- 无法从日志还原一张工单的完整过程。

### 回滚不只是回滚代码

一次发布包含至少五个可以独立回滚的版本：

1. 应用代码；
2. 数据库结构；
3. 知识资料和审核状态；
4. 嵌入模型、协调模型和内容模型；
5. 提示和安全政策。

必须记录哪五个版本一起上线。只把代码退回但保留新向量或新提示，可能仍无法恢复旧行为。

容器化时应使用固定、精简基础镜像和非特权用户；构建密钥不能放进镜像层。Docker 官方明确建议服务尽量用非 root 用户，并用 secret mount 传构建秘密，而不是写进构建参数或镜像环境变量。[Docker 构建建议](https://docs.docker.com/build/building/best-practices/)、[Docker 密钥说明](https://docs.docker.com/build/building/secrets/)

## 13. 成熟做法与本项目的对应关系

| 外部做法 | 谁在用/谁发布 | 本项目怎样采用 | 不能外推什么 |
|---|---|---|---|
| 关系数据和向量同库 | SurveySparrow、施耐德电气的公开 AWS 案例 | 工单关系、来源链和向量同在 PostgreSQL 体系 | 不能证明已达到其规模和成本收益 |
| 元数据先过滤 | Ring 全球客服问答 | 编号、版本、语言先精确过滤 | 不能证明多地区生产能力 |
| 摄取—评测—晋级分离 | Ring | 资料入库、评测、正式可用状态分离 | 领域审核仍需真实工程师 |
| 检索和生成分层评测 | AWS Bedrock 官方方法 | 召回、证据、协调、终态分别计分 | 外部方法不能替代项目题库 |
| 自动评分加人工标注 | 阿里云百炼 | 确定性规则自动判，语义和领域结论人工审 | 当前尚无领域专家标注 |
| 工具调用由应用执行 | 千问官方接口 | 模型选动作，程序校验和执行窄工具 | 结构化输出不代表业务正确 |
| 最小权限和高危人工确认 | OWASP 大模型应用安全指南 | 模型无数据库直写权，高危转人工 | 当前对抗题覆盖仍有限 |
| 全链路追踪 | OpenTelemetry、百炼应用观测 | 规划把工单、检索、模型和数据库写入同一追踪 | 当前只有数据库审计与离线报告 |

AWS 官方也明确建议先独立评估检索，再评估生成，并分别看上下文相关性和覆盖度；这与本项目先测 E5 召回、再测证据判断、最后测工单终态的顺序一致。[AWS 知识库评测方法](https://aws.amazon.com/blogs/machine-learning/evaluate-and-improve-performance-of-amazon-bedrock-knowledge-bases/)

OWASP 的大模型应用安全指南建议最小权限、高风险动作人工批准、区分不可信外部内容并进行对抗测试，与本项目的窄工具、人工接管、来源约束和未见攻击题方向一致。[OWASP 大模型应用安全指南](https://owasp.org/www-project-top-10-for-large-language-model-applications/assets/PDF/OWASP-Top-10-for-LLMs-v2025.pdf)

## 14. 你今天必须亲手完成的五个练习

### 练习一：画主链

不看本文，用一张纸画出从“确认设备和资料”到“解决或转人工”的完整链路，并在每个节点标出事实由数据库、程序还是模型负责。

合格标准：资料版本不能写在模型负责区，数据库内部编号不能写在模型负责区。

### 练习二：解释双分支演示

运行：

```powershell
npm.cmd run demo
```

回答：为什么来源不匹配分支中内容模型调用为 0、方案记录为 0、人工接管为 1？

标准理解：数据库已经能确定来源不匹配，没有必要付费让模型猜；证据不足禁止形成方案，状态机必须转人工。

### 练习三：判断该改哪一层

案例：“正确片段进入前三，但系统选择第一条相似却答非所问的片段。”

标准理解：召回已经完成，问题在精排或证据存在性，不应先换数据库。

案例：“用户要求把第05版当第06版，模型同意。”

标准理解：这是来源约束，必须由程序和数据库处理，不是继续补提示词。

### 练习四：审查一条准确率说法

错误说法：“系统准确率 92.5%，可以生产上线。”

正确改写：“20个项目模拟案例、40轮真实协调决策中，动作与参数正确率为92.5%；该指标不包含真实工厂分布、生产并发和领域方案审核，因此只作为当前模型与提示版本的项目内基线。”

### 练习五：审查部署状态

列出当前从本地演示到测试环境还缺的五项。

参考答案：网络服务入口、持久 PostgreSQL、测试业务空间密钥、全链路观测、构建发布与回滚。还可以补充鉴权、限流、备份和人工接管队列。

## 15. 面试时两分钟讲法

> 第三天我没有继续堆智能体功能，而是做联调、准确率优化和交付收口。联调上，我把配置、数据库、检索、来源、证据、风险、协调和终态拆成八层契约，并建立唯一正式主链，避免专项测试使用新版但正式入口仍使用旧版。准确率上，我把10题扩到40题后，E5首位从90%降到76.7%，但前三仍是100%，所以保留它做候选召回；0.86相似度阈值在新24题上无答案拒答只有83.3%，我没有上线，而是增加独立证据判断。端到端首跑又暴露模型填写数据库编号和来源身份不稳定，我分别改为程序绑定数据库状态、结构化确认来源并数据库精确过滤。第四批来源未见做到11/12、五条无匹配来源程序拒绝5/5、错误来源接收0。交付上完成稳定双分支演示和全量回归，同时明确它仍是本地可重复原型，生产部署还需要服务化、正式 PostgreSQL、观测、备份和小流量发布，避免把演示包装成上线。

## 16. 第三天最后应记住的十句话

1. 组件通过不等于正式业务已经使用；
2. 联调要检查数据库最终状态，不只看模型文字；
3. 模型负责理解文字，程序负责流程许可，数据库负责事实；
4. 首位命中、前三召回、拒答、安全和业务终态不是同一个准确率；
5. 相似度高不等于资料里有答案；
6. 看过的未见集立即变成回归集；
7. 安全硬门不能被总体平均分抵消；
8. 准确率优化先改职责边界，最后才换更大模型；
9. 本地能跑不等于已经部署；
10. 页面位置不能决定知识边界，业务目的和风险边界才能决定知识边界。
