# 第二天教学03：把证据判断接进工单，而不是只停在评测里

## 这一环节做出了什么

我们做出的不是一个新聊天机器人，而是一道强制业务门：检索先给五个候选，证据判断器最多批准其中一个；风险、方案和引用只能继续使用被批准的那一个。

## 你要记住的四个对象

1. **检索运行**：记录“系统找到了什么”，包括前五排名。
2. **证据判断**：记录“这些资料能不能直接回答当前问题”，以及选中了哪一条、哪一页、哪段原文。
3. **风险判断**：记录“被批准的答案是否仍有高危、受限或工程师专用风险”。
4. **处理方案**：只能引用证据判断批准、风险判断允许的命中。

这四层不能混在一起。相关不等于能回答，能回答不等于可以让现场人员执行。

## 为什么判断器不是第二个智能体

它没有自主规划、没有工具选择、不能修改工单。输入只有问题和最多五份候选，输出只有直接回答、部分相关、没有答案三种结论，以及候选编号、页码、引用和理由。程序再检查这些字段是否真实。

协调助手负责推进流程；证据判断器只负责一个窄判断。它们职责不同。

## 为什么必须单独建表

如果把判断写进检索表，就把客观结果和模型结论混在了一起。单独建表后可以问清楚：

- 当时检索到了哪五条？
- 哪个模型、哪个提示版本做了判断？
- 它选了哪条、哪页、哪段原文？
- 风险门后来为什么允许或阻断？

复合外键让数据库自己拒绝跨工单、跨检索、跨片段拼接证据；触发器拒绝事后改写判断。

## 为什么模型调用放在事务外

模型请求可能耗时数秒。如果打开数据库事务后再等网络，会长时间占用锁。正确做法是先读取并检查，关闭短事务；调用模型；模型回来后再开启短事务重新验权和落库。

R225模拟了模型调用期间成员资格被撤销。最终证据判断、风险和接管记录都为0，证明返回后重新验权生效。

## 本轮真实遇到的四个问题

1. 前五中的无关高危片段污染风险判断；修复为风险门只消费选中证据。
2. 协调模型把全部候选写进方案；修复为上下文返回批准编号，方案工具再次硬校验。
3. 明确高危输入仍调用证据模型；修复为固定规则先行，模型调用从1降为0。
4. 旧端到端测试依赖旧链路，首次7项失败；补依赖后又有4项暴露“全部候选可引用”的旧假设，最终22项全部通过。
5. 转人工后的重试先撞上状态门，无法幂等返回；修复为先验权和查历史，再判断新请求状态，模型与数据库记录都不重复。

## 成熟产品怎样印证这套思路

- [Google Cloud答案依据检查](https://cloud.google.com/generative-ai-app-builder/docs/check-grounding?hl=en)对答案候选和参考事实做独立核验，并返回引用。
- [Azure AI Search](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview)返回结构化依据、引用和执行信息。
- [OpenAI智能体实践指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)强调分层护栏和高风险/失败时人工介入。
- [PostgreSQL约束](https://www.postgresql.org/docs/current/ddl-constraints.html)和[触发器](https://www.postgresql.org/docs/current/trigger-definition.html)负责让关系和只追加规则不依赖应用程序自觉。

它们的权威性来自各自产品或项目维护方；只能证明接口与工程方法，不能证明我们的工业数据已经正确。

## 你现在能讲出的项目逻辑

> 我没有把向量检索首位直接交给方案生成。前五只作为候选，千问窄判断器确认资料能否直接回答，程序再核对候选、页码和逐字引用。判断记录独立只追加，复合外键保证它属于当前工单和检索。风险门只消费被批准的命中；部分相关、无答案、模型异常都转人工，明确高危输入甚至跳过模型直接阻断。
