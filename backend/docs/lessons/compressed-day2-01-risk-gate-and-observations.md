# 三天计划第二天第一节：现场观察、风险门和人工接管

## 这一节做出了什么

协调助手现在有两项新的受限能力：

```text
append_observation
  → 只追加现场现象、动作或测量
  → 不覆盖历史
  → 草稿或等待补充信息时回到排查中

run_risk_assessment
  → 从工单绑定的检索记录读取证据
  → 执行固定规则
  → 合并可选的模型升级意见
  → 允许方案或原子创建人工接管
```

## 为什么风险不能只交给模型

模型擅长理解“好像要拆开看看”这类自由表达，但相同输入可能产生不同判断。固定的危险标识、工程师专用资料和受限设置不能依赖提示词记忆。

因此最终风险使用“只能升、不能降”的合并方式：

```text
程序风险：high
模型建议：low
最终结果：high

程序风险：low
模型建议：high
最终结果：high
```

这不是不信任模型，而是把不允许变化的责任交给确定性程序，把需要理解语言的部分交给模型。

## 为什么零结果也要转人工

零结果不等于没有风险，只表示当前有效资料中没有足够证据。继续生成方案会把模型常识伪装成厂商结论。

因此系统会保存“证据不足”的正式判断，创建独立原因的人工接管，而不是标成高危。高危和资料不足都停止自动方案，但业务原因不同，后续改进方式也不同。

## 为什么风险判断必须绑定检索运行

如果只保存`high`或`low`，以后无法知道当时看过哪些片段。现在每次判断都绑定：

- 具体工单；
- 具体检索运行；
- 具体检索命中；
- 规则代码和版本；
- 程序风险、模型风险和最终风险；
- 转人工原因和工单事件。

## 现场观察为什么只追加

第二版方案必须基于新信息。如果允许覆盖旧描述，系统无法证明第二版比第一版多知道了什么。

观察按症状、已做动作、测量、环境和用户反馈分类，正文和分类一起进入不可变工单事件。其他厂区成员、停用账号和等待人工后的自动排查都被拒绝。

## 这次真实遇到的问题

测试设备最初没有规范型号，数据库拒绝创建。正确处理不是删除非空约束，而是修正测试夹具。这证明反向约束也在审查我们的测试数据。

实现风险判断后又发现“状态已经等待人工”不等于“存在人工接管记录”。如果只有状态，无法分派、接单或统计原因。新增失败测试后，把风险判断、接管记录、时间线和状态变化放进同一事务。

## 你应该记住

1. 检索正确不等于允许操作，中间必须有风险门。
2. 固定规则给出不可降低的底线，模型只能补充更高风险。
3. 没证据时拒绝生成，是能力边界，不是系统故障。
4. 高危和证据不足都转人工，但必须保存不同原因。
5. 状态变化不等于业务记录完整，等待人工必须有真实接管记录。
6. 现场观察只能追加，才能证明第二版方案使用了什么新信息。
7. 数据库约束不仅审查生产输入，也会暴露测试夹具造假或遗漏。

## 下一步

实现带证据的第一版方案、进入等待现场确认、记录失败反馈，并用新观察约束第二版方案，最后由数据库禁止第三版。
