# 自动化测试与准确率提升流程

## 1. 先分清“代码正确”和“模型效果好”

这是两个不同问题，必须用不同测试回答。

| 问题 | 例子 | 验证方式 | 结果形式 |
|---|---|---|---|
| 代码和业务约束是否正确 | 禁止第三版方案、错厂区不能查工单、规则命中后必须转人工 | 数据库约束、单元测试、服务测试、端到端测试 | 通过或失败 |
| 模型效果是否足够 | 检索第一名是否正确、无答案能否拒答、协调模型动作是否正确 | 固定题库、真实模型、计分器、预设门槛 | 指标、通过、失败或受阻 |

默认回归通过只能证明第一类和评测代码本身没有坏，不能自动证明所有模型门槛都达标。

## 2. 为什么有默认跳过项

`npm test`承担可重复、无费用、尽量不受外部网络影响的回归。需要本地模型文件、付费接口或专属密钥的测试通过环境变量显式开启。

默认跳过不等于通过，也不等于没做。每项只能处于三种真实状态：

- 通过：真实模型已经运行并达到门槛；
- 失败：真实模型已经运行，但效果没达到门槛；
- 受阻：没有进入模型计算，不能评价模型效果。

当前登记表由R204自动审查，运行：

```powershell
npm.cmd run report:model-tests
```

## 3. 自动化测试是怎样从业务问题长出来的

```text
真实业务风险
  → 写成一句不可违反的规则
  → 准备输入、正确结果和来源
  → 先写一个会失败的测试
  → 实现最小代码或数据库约束
  → 跑局部测试
  → 跑完整回归
  → 保存失败、调整和复测证据
```

以“屏蔽OHF保护”为例：

1. 业务风险：检索第一名可能是低风险片段，导致危险请求被放行；
2. 规则R198：明确关闭保护时不能依赖检索排名才阻断；
3. 失败测试：故意让低风险片段排第一，系统实际返回`proposal_allowed`；
4. 实现：数据库增加版本化输入意图规则；
5. 误判测试R199：风险询问和被动状态不能误拦；
6. 端到端R200：协调助手只能检索、判断风险、转人工，方案数必须为0。

这比“让AI帮我测一下”更严格，因为正确结果、边界和数据库终态都提前定义好了。

## 4. 六层测试结构

### 第一层：数据库不可违反的规则

测试外键、唯一性、状态转换、不可修改记录、事务回滚和第三版方案禁止。模型无论怎样输出，都绕不过这一层。

### 第二层：纯函数和数据结构

测试题库重复编号、伪造页码、分数计算、阈值边界、模型返回结构和规则配置。速度快，任何代码修改都运行。

### 第三层：窄工具服务

使用固定测试向量或假模型，验证权限、产品范围、幂等、事务和留痕。假模型只用于制造可控输入，不能作为真实准确率证据。

### 第四层：完整业务链

从草稿工单跑到检索、风险、方案、现场反馈、恢复或人工接管，并检查数据库最终状态。这里验证的是整个系统，不只看模型说了什么。

### 第五层：真实模型能力门

使用固定题库和真实E5、千问或排序模型，计算首位、前三、拒答、动作、参数和整条过程指标。联网前先冻结题库、模型版本、提示版本、文件摘要和门槛。

### 第六层：真实业务验收

使用真实工厂问题和领域工程师标签，统计误答、漏答、误转人工、危险漏拦和处理时间。本项目尚未进入这一层，不能把开发集指标叫生产准确率。

## 5. 准确率题库怎样划分

| 数据区 | 用途 | 能不能反复看结果调方案 |
|---|---|---|
| 开发集 | 找问题、比较方案、形成候选参数 | 可以，但每次调整要留痕 |
| 留出集 | 第一次验证候选是否能泛化 | 不可以看完后继续调并在同集宣布成功 |
| 回归集 | 保存已经解决的真实失败，防止以后复发 | 可以反复运行，但不能当新能力证明 |
| 真实验收集 | 领域人员从真实业务中标注 | 只能按既定验收流程使用 |

本项目的40题是开发集；24题在第一次运行时是0.86阈值留出集，结果暴露后已经转为回归集；36题在策略锁定后首次运行时是项目内未见集，运行结束后同样只能作为回归数据。随后新增的18道三分类题在R243前封存，首跑11/18失败；从R243结束起，这18题以及后续R247、R255都只能算回归。R198和R200这类已经修复的失败也进入长期回归集。

## 6. 不同能力看什么指标

### 检索

- 首位命中：第一条能否直接支撑后续判断；
- 前三命中：第一段召回有没有把正确片段找回来；
- 平均倒数排名：正确片段总体排得多靠前；
- 错型号拒答：是否阻止跨产品族；
- 无答案拒答：语料没有答案时是否停止；
- 接收准确率：所有被系统放行的结果中有多少真的正确。

### 证据判断

- 类别准确率：直接回答、部分相关、完全不可回答是否判对；
- 证据接受率：所选候选是否属于运行前定义的可接受证据集合；
- 联合准确率：类别和证据是否同时正确；
- 引用有效率：页码和逐字引用是否能被程序验证；
- 高危误放行：预期拒答或部分相关却被判直接回答的次数，必须单独统计。

不能用“唯一候选编号命中”代替类别准确率。一个问题可能有多份官方资料支持同一前提；题库应在首跑前保存`acceptable_candidate_ids`，而不是运行后强迫只认一份。

### 协调助手

- 结构输出率：返回能否被程序解析；
- 动作正确率：是否选了当前应做的工具；
- 参数正确率：编号和内容是否正确；
- 整条过程通过率：多轮下来有没有走到正确业务终态；
- 危险越权次数：必须为0。

### 风险门

- 高危召回：危险输入是否全部阻断；
- 误阻断率：正常询问是否被错误转人工；
- 零方案率：高危案例是否始终不生成方案；
- 接管完整率：风险、规则、工单状态和事件是否全部留痕。

不能只报一个“总体准确率”，因为总体数字会掩盖危险漏拦和无答案乱答。

## 7. 当前准确率究竟卡在哪里

### 第一段召回暂时不是最大问题

40题中E5对30道可回答题前三命中100%，说明正确片段能进入候选。现在不应急着换更大嵌入模型。

### 第一名细排仍需提高

E5首位76.7%，门控混合73.3%。正确片段在前三但不是第一，说明需要二次排序，而不是继续堆同义词。R196已准备90%门槛，但缺合法后端排序密钥。

### 无答案判断已通过独立能力门并接入主链路

0.86留出测试得到无答案拒答83.3%、接收准确率84.6%，因此阈值没有上线。改为E5前五候选加独立证据判断后，旧24题回归四项100%；新36题首次运行得到94.4%有答案正确放行、100%无答案拒答、100%放行准确率和0次判断错误。当前已由R222—R229接入工单主链路，部分相关、模型异常、权限竞态和转人工后幂等重放均形成预期数据库终态；结论仍限于项目编写数据。

R230—R233进一步把直接回答、无答案、部分相关和明确高危四条分支及其数据库终态在真实调用前封存。首轮R233精确分类3/4，按4/4门槛失败，但四条安全终态4/4。根因是“部分相关”和“无答案”定义重叠；保留首轮报告后只增加互斥分类边界，R236在已暴露四题上回归4/4、判断错误0。第二版结果只能证明已知失败修复，下一轮必须换新未见题。

换成18道新题后，R243首次未见首跑只有11/18，直接证明第二版4/4没有推广。第三版单次完整提示回归15/18；第五版将判断重构为“模型核对三个事实—程序生成类别—模型摘录证据—程序校验原文”，原联合指标16/18仍失败，但类别为17/18，高危误放行和判断错误均为0。V307在完整回归前已记录为多证据歧义，独立审定分析为17/18；原R255失败状态不变。当前不再针对这18题调提示，下一次能力声明必须来自工程师审核的新未见集。

随后保持第五版策略不变，重新建立第三批18道从未运行的问题，并在首跑前把可接受证据集合写入题库。R262唯一首跑类别17/18、多证据联合17/18；直接回答5/6、部分相关6/6、完全不可回答6/6，高危误放行和判断错误均为0，达到全部冻结门槛。这证明策略能推广到本项目的新问法，但候选仍是六份旧摘录且没有领域工程师审核，所以仍不是生产验收。

### 协调动作存在业务歧义

真实40轮中结构输出100%，动作和参数92.5%，整条过程85%。三个失败是模型先记录用户输入而不是立即检索。R188修复了重复消费，但下一轮还要允许多个同样合法的中间动作，并以最终数据库状态评分。

## 8. 提高准确率的正确顺序

1. 先检查标签和官方来源是否正确；错误答案不能训练出正确系统。
2. 按错误类型分组：没召回、排错、应拒答、跨型号、高危漏拦、动作歧义。
3. 一次只改一个环节，避免不知道提升来自哪里。
4. 开发集上形成候选方案，不宣布成功。
5. 冻结新留出集、指标和门槛后再运行。
6. 通过后把真实失败加入回归集。
7. 换模型、提示、切片或规则版本时，重跑相关能力门和全量回归。
8. 上线后用真实查询和人工复核监控数据漂移。

## 9. 当前后续实验顺序

1. 新建工程师审核的未见集：每题在首跑前分别冻结预期类别和可接受证据集合，不能重复引用R243—R255成绩。
2. 引入真实问题：让设备工程师审核候选资料，并从脱敏真实工单中建立外部验收集。
3. 二次排序：取得合法后端密钥，执行R196；若不可得，选择可本地固定版本的排序模型做同题对照。
4. 严格模型身份：当前官方声明`qwen3.7-plus`等效于`qwen3.7-plus-2026-05-26`，但令牌资源包未直接请求快照名；生产应换到支持快照名或部署编号的入口后重建能力门。
5. 生产监控：记录模型版本、题型、是否转人工、最终解决结果和人工纠正原因。

## 10. 明确禁止的“提准”方式

- 看完留出集后调阈值，再在同一留出集宣布通过；
- 只挑成功案例写报告；
- 把HTTP 401记作模型0%或模型通过；
- 把默认跳过写成通过；
- 用假向量测试冒充真实E5准确率；
- 只看平均值，不看高危漏拦和无答案误答；
- 修改题目标签来配合模型输出；
- 把可能存在多份合理证据的题强制成唯一候选，再把合理的另一候选计为分类错误；
- 只报审定后的分数，不同时报告原冻结结果；
- 没有领域审核就声称工业维修答案正确。

## 11. 成熟实践依据

- [Anthropic Agent评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)提出任务、试验、评分器、过程记录和最终状态的区分，并强调正反样本平衡、开发能力评测与回归评测分开；文中也介绍Claude Code、Descript和Bolt团队的评测实践。
- [Anthropic固定工作流与智能体方法](https://www.anthropic.com/engineering/building-effective-agents)区分代码预定路径的工作流和模型自主编排的智能体，并明确复杂度会增加时延和成本；本项目据此没有把两个窄步骤包装成多智能体。
- [阿里云百炼结构化输出文档](https://help.aliyun.com/en/model-studio/qwen-structured-output)说明`json_object`接口并建议程序继续验证字段和格式；本项目在JSON解析后仍检查布尔一致性、候选、页码和连续原文。
- [微软研究院评分不确定性研究](https://www.microsoft.com/en-us/research/publication/validating-llm-as-a-judge-systems-under-rating-indeterminacy/)说明强制单标签会在存在多种合理解释时扭曲评测，并给出多标签答案集合思路；本项目据此把类别和可接受证据集合分开。
- [OpenAI Agent实践指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)建议从单Agent开始，使用分层护栏和人工介入，并根据真实失败持续补充规则。
- [Elastic混合检索文档](https://www.elastic.co/docs/solutions/search/hybrid-search)和[kNN文档](https://www.elastic.co/docs/solutions/search/vector/knn)提供关键词、向量、融合、重排和最低相似度等成熟产品能力，但参数仍需当前业务自己验证。
- [微软多语言E5技术报告](https://www.microsoft.com/en-us/research/?p=1100727)由模型研究与发布团队说明不同规模模型的质量和效率取舍，不为本项目准确率背书。

这些资料的权威范围是其产品能力、研究结果或工程方法；本项目的题库、阈值、中文规则和指标必须由自己的测试负责。
