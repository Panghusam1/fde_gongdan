# 工单业务流程第一版

本文件汇总学习者已经确认的决定，并补充不值得逐项追问的保守默认值。默认值可以在阶段审查时集中修改。

## 已由学习者确认

1. 确认厂区和设备后立即创建草稿工单，并记录全过程。
2. 高危工单只能由有权限的人工工程师确认解决。
3. 普通问题由AI提供有证据的低风险方案，现场用户确认实际恢复。
4. AI给出合格方案后，工单进入“等待用户确认”。
5. 同一工单最多允许两版低风险方案；第二版仍失败则转人工。

## 完整主流程

```text
验证用户和厂区权限
→ 确认厂区、设备、厂商、系列和具体型号
→ 创建草稿工单和第一条工单事件（同一事务）
→ 记录故障码、现场现象、已做事项和未做事项
→ 工单进入排查中
→ 按厂区、厂商、系列和型号强制过滤资料
→ 执行关键词与向量检索
→ 保存检索条件、候选片段和最终引用证据
→ 判断证据是否充分
   ├─ 证据不足：等待人工
   └─ 证据充分：生成下一步方案
→ 判断方案风险
   ├─ 高危：停止自动指导并等待人工
   └─ 低风险：保存方案版本并等待用户确认
→ 用户反馈
   ├─ 已恢复：记录确认并进入已解决
   ├─ 第一版未恢复且有新证据：重新排查并生成第二版
   ├─ 第二版未恢复或无新证据：等待人工
   └─ 新信息触发高危：等待人工
→ 人工工程师接单后进入人工处理中
→ 保存人工处理记录和结果
→ 有权限人员确认后进入已解决
→ 完整性检查通过后关闭
```

## 状态第一版

| 状态代码 | 中文名称 | 进入条件 |
|---|---|---|
| `draft` | 草稿 | 厂区和设备已经确认 |
| `investigating` | 排查中 | 已提交故障信息或失败结果后重新排查 |
| `awaiting_information` | 等待补充信息 | 缺少用户能够补充的型号或现场信息 |
| `awaiting_user_confirmation` | 等待用户确认 | 已存在有证据且通过低风险检查的方案 |
| `awaiting_human` | 等待人工 | 高危、资料不足、两版失败或无新增证据 |
| `human_processing` | 人工处理中 | 有权限的工程师已经接单 |
| `resolved` | 已解决 | 普通问题由现场用户确认恢复；高危问题由工程师确认 |
| `closed` | 已关闭 | 必填记录完整且由有权限人员确认关闭 |
| `cancelled` | 已取消 | 误建或重复工单；历史记录仍保留 |

## 保守默认值，不单独逐项提问

- AI永远不能直接把工单标记为已解决或已关闭。
- 关闭后的工单不直接修改；再次发生问题时创建关联的新工单。
- 取消工单只改变状态，不删除历史数据。
- 资料不足与高危阻断都转人工，但必须记录不同原因。
- 所有状态变化都保存原状态、新状态、操作者、理由和时间。
- AI生成内容、用户确认内容和工程师结论分开保存。
- 超时提醒时长由企业配置，第一周不把任意小时数写死在数据库中。

## 本阶段集中检查点

业务流程只有在以下核心方向需要修改时才返工：

- 是否反对全过程工单。
- 是否反对普通问题由现场用户确认、高危问题由工程师确认。
- 是否反对两版方案上限。
- 是否反对资料不足或高危时转人工。
